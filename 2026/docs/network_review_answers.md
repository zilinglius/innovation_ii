# 第 01 讲回顾讲义：参考答案

> 配合 `network_review.md` 使用。每题末尾用“→”标注讲义出处，方便回头重读；数值以讲义里那次实测为准（ns1 的 `veth1` 为 `ba:d6:9f:0e:7d:da`，ns2 的 `veth2` 为 `3e:fb:bd:fb:27:d2`）。第九节的“想一想”是开放题，给出的是参考思路，不是唯一答案。

## 一、从 `ip addr show` 开始

1. `veth1@if9` 中的 `@if9` 是对端接口的索引号，`link-netns ns2` 是对端所在的 namespace。veth 是成对创建的，内核为每一端都记录了另一端在哪，所以任何一端的信息里都能看到对端——这就是“成对存在”的直接证据。对端在 ns2 里，接口编号 9，也就是 `veth2`。→ 6.2 节、6.4 节步骤三
2. `ba` = `1011 1010`。最低位 b0 = 0，单播；次低位 b1 = 1，本地管理地址（Locally Administered）。veth 的 MAC 由内核随机生成，规定为本地管理的单播地址，首字节的低两位固定是 `10`，因此首字节低 4 位只能是 `0010`、`0110`、`1010`、`1110`，即第二个十六进制数字只能是 `2`、`6`、`a`、`e`。它不是厂商烧录的，查不到对应的 OUI。→ 2.1 节
3. MTU 限制的是帧的数据载荷（上层交下来的 IP 包）的最大长度，不含 14 字节帧头与 4 字节 FCS。1500 + 14 + 4 = 1518（带 802.1Q 标签时 1522）。`lo` 为 65536 说明 MTU 是**每个接口**的属性，不是全局常数：环回接口不经过任何物理链路，内核可以给它更大的值。→ 2.3 节
4. 多出 `inet6 fe80::…/64 scope link` 一行。这是链路本地地址：只要系统启用了 IPv6，接口一 UP，内核就按 `fe80::/10` 前缀自动生成一个（无状态自动配置的一部分），不需要任何配置；同时还会发出几个 NDP / MLD 组播报文。→ 3.4 节末尾的 NOTE、6.4 节步骤三

## 二、路由表里的第一条路由

5. 内核自动加的：给接口配上 `192.168.1.1/24` 并把接口 UP 之后，内核为这个网段生成一条**直连路由**。`proto kernel`：路由来源是内核自动生成（区别于管理员手工 `ip route add` 或路由协议写入）；`scope link`：目的地在本链路上直接可达，不需要网关；`src 192.168.1.1`：从这条路由发包时默认使用的源地址。→ 3.1 节第 5 小点、6.4 节步骤三
6. 用**本机接口的掩码**分别与本机 IP、目的 IP 做按位与，结果相同即同网段。同网段：对目的 IP 本身做 ARP，直接交付；不同网段：对网关（下一跳）的 IP 做 ARP，帧发给路由器，而 IP 首部的目的地址仍是最终目的地。`/26` 的掩码是 `255.255.255.192`：`100 & 192 = 64`，`120 & 192 = 64`，同属 `192.168.1.64/26`（可用 `.65`–`.126`）；`130 & 192 = 128`，属于 `192.168.1.128/26`，不同网段。→ 3.1 节第 4、5 小点
7. 立刻报 `ping: connect: Network is unreachable`。一个帧都不会发出：ns1 的路由表只有 `192.168.1.0/24` 一条直连路由，没有任何条目能匹配 `10.0.0.1`，内核在发送之前就拒绝了；ARP 是为“已经决定从哪个接口发给谁”服务的，连接口都定不下来，自然不会发 ARP。→ 3.1 节第 5 小点、模块七思考题 3

## 三、读懂 `ping` 的输出

8. 56 是 ICMP 数据的长度；84 = 56 + 8（ICMP 首部）+ 20（IP 首部），即 IP 数据报的总长度。回复行的 `64 bytes` = ICMP 首部 + 数据 = 8 + 56。tcpdump 的 `length 98` = 84 + 14 字节以太网帧头（不含 FCS）。→ 2.2 节 NOTE、6.4 节步骤三
9. 是**对方回复包**（Echo Reply）到达本机时的 TTL。Linux 发包的默认初始 TTL 是 64（`net.ipv4.ip_default_ttl`），直连链路上没有经过任何路由器，所以没有被减过。跨两台路由器后会显示 `ttl=62`。→ 3.2 节 TTL 一行、6.4 节步骤三
10. 封装在 IP 数据报里，协议号 `1`；功能上属于网络层。Echo Request 是 Type 8，Echo Reply 是 Type 0，Code 都为 0。→ 3.5 节

## 四、六个帧：ARP 与 ICMP

11. 步骤三的 `ping` 已经让双方的 ARP 缓存里有了对方，缓存命中就不会再广播 ARP；不清空的话第 1、2 帧（广播的 Request 与其 Reply）不会出现，只能看到第 3、4 帧的 ICMP，以及表项变为 `STALE` 后复查时的一对单播 ARP（类似第 5、6 帧）。→ 6.4 节步骤四
12. 六个帧：→ 2.2、2.4 节，6.4 节步骤四

    | 序号 | 类型 | 目的 MAC | EtherType |
    | :--- | :--- | :--- | :--- |
    | 1 | ARP Request（ns1 → 所有人） | `ff:ff:ff:ff:ff:ff`，广播 | `0x0806` |
    | 2 | ARP Reply（ns2 → ns1） | `ba:d6:9f:0e:7d:da`，单播 | `0x0806` |
    | 3 | ICMP Echo Request（ns1 → ns2） | `3e:fb:bd:fb:27:d2`，单播 | `0x0800` |
    | 4 | ICMP Echo Reply（ns2 → ns1） | `ba:d6:9f:0e:7d:da`，单播 | `0x0800` |
    | 5 | ARP Request（ns2 → ns1，复查） | `ba:d6:9f:0e:7d:da`，单播 | `0x0806` |
    | 6 | ARP Reply（ns1 → ns2） | `3e:fb:bd:fb:27:d2`，单播 | `0x0806` |

13. Request 必须广播，因为发送方只知道对方的 IP、不知道 MAC，只能问链路上的所有人。Reply 可以单播，因为 Request 里已经带了 ns1 的 MAC（`tell 192.168.1.1` 以及帧头的源 MAC），ns2 直接回给它即可。ns2 在收到第 1 帧时就“顺便”记下了 ns1 的 IP → MAC 映射，所以回复 ICMP 时不必再发 ARP。→ 2.4 节时序图、6.4 节步骤四
14. ns2 发起的。它那条关于 ns1 的表项是从广播 Request 里顺便学来的，从未经过确认；用它发出第 4 帧之后，内核按邻居表的状态机 `STALE → DELAY → PROBE`，发一个**单播** ARP Request 向 ns1 求证（`DELAY` 阶段默认等 5 秒，所以第 5 帧出现在约 5 秒后），收到 Reply 后表项才置为 `REACHABLE`。→ 2.4 节末段、6.4 节步骤四第 4 点
15. 42 = 14（帧头）+ 28（ARP 报文）；98 = 14 + 20（IP 首部）+ 8（ICMP 首部）+ 56（数据）。“至少 64 字节”是**线路上**的以太网帧的要求，由发送方网卡或驱动填充；tcpdump 看到的是**内核里**的帧，抓包点在填充与 FCS 之上，所以既不含填充也不含 FCS；veth 又是纯软件设备，本来就不填充、不算 FCS。→ 2.2 节 NOTE
16. `-n`：不做名字解析，IP 与端口都显示数字；`-e`：打印以太网帧头（源 / 目的 MAC、EtherType、帧长）；`-i veth2`：在 `veth2` 接口上抓；`arp or icmp`：过滤表达式，只保留 ARP 与 ICMP。去掉过滤表达式后会混进 ICMPv6 的路由器请求（RS）、MLD 等组播报文，如 `IP6 … ICMP6, router solicitation`。→ 3.4 节末尾的 NOTE、6.4 节步骤四

## 五、亲手抓到的分片

17. 3972（数据）+ 8（ICMP 首部）+ 20（IP 首部）= 4000。三片：`length` 1500 / 1500 / 1040；`offset`（字节）0 / 1480 / 2960；MF = 1 / 1 / 0（tcpdump 显示为 `flags [+]`、`[+]`、`[none]`）。首部里的 Fragment Offset 以 8 字节为单位，实际存的是 0 / 185 / 370。三片的 `id 35846` 相同——靠 Identification 字段被认出属于同一个数据报。→ 3.2、3.3 节
18. ICMP 首部（8 字节）只在第一片的载荷开头；后两片的载荷是纯数据，tcpdump 只能从 IP 首部 `proto ICMP (1)` 知道“这是 ICMP 的一部分”，无从解析 Type / Code，于是显示 `ip-proto-1`。对应“工程弊端”第 2 条：只有第一个分片带有传输层首部（端口号），防火墙、NAT 以及按五元组做负载均衡的设备都难以正确处理后续分片。→ 3.3 节 WARNING、6.4 节选做观察 A
19. 1472 + 8 + 20 = 1500，恰好等于 MTU，不必分片；1473 则超出 1 字节，必须分片。DF = 1 表示“不允许分片”：本机 IP 层发现需要分片又不允许，直接在本地报错 `local error: message too long, mtu=1500`，报文根本没有发出。如果超出发生在路径中间的路由器上，路由器会丢弃报文并回送 ICMP Type 3 / Code 4（Fragmentation Needed，携带下一跳 MTU），源主机据此调小后续报文——这就是 Path MTU Discovery。→ 3.2 节 Flags 一行、3.3 节 WARNING、3.5 节

## 六、一条 TCP 连接的一生

20. 五元组：(`192.168.1.1`, `43404`, `192.168.1.2`, `9000`, TCP)。43404 是 ns1 的内核在发起连接时临时分配的（Ephemeral Port）；Linux 默认范围 32768–60999（`net.ipv4.ip_local_port_range`），IANA 的建议范围是 49152–65535。→ 4.1 节
21. SYN 虽然不携带数据，却规定占用一个序号，所以对 `seq = x` 的确认号是 `x + 1`：1087888725 + 1 = 1087888726。占一个序号是为了让 SYN 本身也能被确认——确认号必须能区分“收到了 SYN”与“什么都没收到”，SYN 丢失时也能靠这套机制发现并重传。两次握手的问题：一个在网络中滞留许久的**旧 SYN** 到达时，服务端会白白建立连接、分配资源；第三次握手让服务端确认“客户端此刻确实想建立这条连接，并且收到了我的初始序号”。→ 4.4 节
22. MSS = MTU − IP 首部 − TCP 首部 = 1500 − 20 − 20 = 1460（不带选项时）。→ 模块七思考题 2
23. 握手完成后 tcpdump 改为显示**相对序号**（相对于各自的初始序号），所以 `1:11` 表示第 1 到第 10 个字节（绝对序号 1087888726–1087888735），`length 10`。`ack 11` 的意思是“期望收到的下一个字节的序号是 11”，即第 1–10 字节全部收到。累积确认：一个确认号表示此序号之前的所有字节都已完整收到，不需要逐段确认。→ 4.3 节 Seq / Ack 两行、6.4 节选做观察 B
24. 抓包应见 14 + 20 + 20 + 10 = 64 字节；实测 76，多出的 12 字节是 TCP 首部里的时间戳选项（`nop, nop, TS val … ecr …`，1 + 1 + 10 字节），真实的 TCP 首部是 32 字节而非 20 字节：14 + 20 + 32 + 10 = 76。SYN 报文携带的选项更多——`mss`（4）+ `sackOK`（2）+ `TS`（10）+ `nop`（1）+ `wscale`（3）= 20 字节，首部 40 字节，所以帧长 14 + 20 + 40 = 74。→ 5.1 节、6.4 节选做观察 B
25. 少了服务端单独的 ACK：服务端恰好也没有数据要发，把“对客户端 FIN 的确认”与“自己的 FIN”合并成了一个 `[F.]` 报文。主动关闭的是客户端 ns1（`nc -N` 在输入结束后关闭连接），它最后进入 `TIME_WAIT`，Linux 停留 60 秒；目的有二：最后一个 ACK 丢失时对方会重传 FIN，本方还能重发 ACK；让属于旧连接的报文在网络中自然消失，避免混进同一五元组的新连接。→ 4.4 节

## 七、不看输出也要会

26. 应用层：报文（Message）；传输层：报文段（Segment，TCP）/ 数据报（Datagram，UDP）；网络层：分组 / 包（Packet）；数据链路层：帧（Frame）；物理层：比特流（Bits）。`length 98` 是数据链路层的**帧**的长度（不含 FCS）。→ 1.1 节、2.2 节 NOTE
27. 讲义的表是按**功能**归层的：OSPF 与 BGP 解决的都是网络层的选路问题，虽然承载方式不同（OSPF 直接在 IP 上，BGP 在 TCP 上）。ARP 报文直接封装在以太网帧里、不经过 IP，但它服务的是 IP（把 IP 地址映射为 MAC），所以被看作二、三层之间的“胶水”。→ 1.2 节 NOTE、2.4 节
28. `/27` 的掩码是 `255.255.255.224`。77 = `0100 1101`，与 `1110 0000` 按位与得 64：网络地址 `10.0.1.64`；广播地址 `10.0.1.95`；可用主机 `10.0.1.65`–`10.0.1.94`，共 $2^5 - 2 = 30$ 个。→ 3.1 节第 4 小点
29. 变了的：帧头里的源、目的 MAC 整体换新（帧 1 是 `MAC_A → MAC_Router_In`，帧 2 是 `MAC_Router_Out → MAC_B`），IP 首部的 TTL 减 1（64 → 63），首部校验和随之重算。不变的：源 IP、目的 IP、TCP 报文段与数据。六步顺序：① 网卡收到帧，FCS 校验通过 → ② 目的 MAC 是自己的接口，剥掉二层帧头 → ③ 取出 IP 包，查路由表匹配下一跳 → ④ TTL 减 1，重新计算 IP 首部校验和 → ⑤ 查 ARP 表，得到下一跳的 MAC → ⑥ 重新封装新的二层帧头，发出帧 2。→ 5.2 节
30. 以太网帧头的 EtherType（`0x0800` → 交给 IP）、IP 首部的 Protocol（`6` → 交给 TCP）、TCP 首部的目的端口（`9000` → 交给监听该端口的套接字）。→ 5.3 节
31. 网络接口、IP 地址、路由表、ARP / 邻居表、端口空间、防火墙规则（iptables / nftables）、大部分内核网络参数（`sysctl net.*`）。可以同时监听：端口空间是按 namespace 隔离的。`ip_forward` 每个 namespace 各一份，所以第 02 讲可以只在某个 namespace 里打开转发、把它变成路由器，而不影响宿主机和其他 namespace。→ 6.1 节
32. 命令序列（`sudo` 略）：→ 6.3、6.4 节

    ```bash
    ip netns add ns1
    ip netns add ns2
    ip link add veth1 type veth peer name veth2
    ip link set veth1 netns ns1
    ip link set veth2 netns ns2
    ip netns exec ns1 ip addr add 192.168.1.1/24 dev veth1
    ip netns exec ns1 ip link set veth1 up
    ip netns exec ns2 ip addr add 192.168.1.2/24 dev veth2
    ip netns exec ns2 ip link set veth2 up
    ip netns exec ns1 ping -c 3 192.168.1.2
    ```

    直连路由在 `ip addr add … dev veth1` 配好地址、并且 `ip link set veth1 up` 之后才出现：地址加上而接口仍是 DOWN 时，`ip route show` 还是空的；对端尚未 UP 时这条路由会带 `linkdown` 标记。清理只需 `ip netns del ns1`、`ip netns del ns2`，附着在 namespace 上的 veth 由内核自动回收，不必单独删除。
33. 思考题：→ 模块七思考题 1、4、5
    - MAC 地址是扁平的、非层次化的（前 24 位是厂商，与地理或拓扑位置无关），无法按前缀聚合，路由器只能为每台设备各存一条表项，全球路由表会无限膨胀；IP 地址有网络号 / 主机号的层次，才能用一条 `/24` 概括一整个网段。
    - Network Namespace（把容器的网络栈隔离出来）与 iptables / NAT（把宿主机 8080 端口的流量重定向到容器的 80 端口）。
    - 靠 veth 拼不出“同一个网段”：veth 只有两端，三个 namespace 两两拉线要三对 veth、每个 namespace 两个接口，得到的是三条互相独立的点对点链路而不是一个广播域（一个广播帧只能到达一个邻居；再加一个 namespace 又要多拉三根线）。缺的是能把多个接口接成一个广播域的二层交换设备——网桥（bridge），Linux 内核自带软件实现，是第 02 讲的第一个主角。

## 九、“想一想”参考思路

- **启发 1**：消息队列里的消息元数据（主题、路由键、消息 ID），RPC 框架的信封（服务名、方法名、请求 ID），HTTP 首部之于 body——它们都只放分派所需的信息，对载荷内容不做解释；载荷就是序列化后的业务数据。
- **启发 2**：正确的流式解析器要跨数据块保存状态（缓冲不完整的首部、记住“还差多少字节”），不能假设一次读到的数据块恰好是一条消息；tcpdump 对分片“解析不下去”正是因为它按单个报文、无状态地解析。
- **启发 3**：TCP 用序号去重——重复到达的报文段按序号识别并丢弃，应用层只会收到一份。应用层的对应物是请求 ID / 幂等键（idempotency key）：服务端记住已处理的 ID，重复请求返回同一结果而不重复执行。
- **启发 4**：`recv()` 的调用次数无法预测——取决于内核如何把字节流切成报文段（MSS、发送时机、GSO 等）、接收缓冲区与进程被调度的时机。TCP 只保证字节不丢、不重、按序到达，不保证任何边界；1 MB 可能一次收几十 KB、也可能收几个字节。
- **启发 5**：只有“有 / 没有”两态时，要么每次过期都重新广播（每个邻居每 30 秒一次，链路上充满 ARP），要么永不过期（对方换了网卡或虚拟机迁移后，错误的 MAC 一直用下去，流量静默丢失）。多状态让正常情况下零开销、异常时能自动纠正。
- **启发 6**：给每个请求编号（请求 ID 或序号），响应带回同一个编号，客户端只接受编号匹配、且仍在等待中的响应，其余丢弃；进程重启后换一个纪元（epoch）前缀，旧纪元的响应一律不认。
- **启发 7**：数据先堆在套接字发送缓冲区，缓冲区满了之后堆在你的进程内存里（无界队列），内存持续增长直到耗尽；阻塞或 `EAGAIN` 就是内核在对生产者说“慢一点”，这正是背压信号，去掉它等于关掉了保护。
- **启发 8**：40 片全部到达才算成功，概率是 0.99 的 40 次方 ≈ 0.67，即约三分之一的数据报要整个重传；改成 40 个独立的 TCP 报文段，平均只有 0.4 个报文段需要重传，而且只重传丢的那一段。
- **启发 9**：容器有自己的 network namespace，其中的 `lo` 与宿主机的 `lo` 是两个不同的接口，端口空间也是隔离的（6.1 节）；容器里的 `localhost` 指的是容器自己的回环接口，宿主机上监听的 8080 不在其中。
- **启发 10**：常见的四处：数据帧 76 字节而非 64（时间戳选项）；ARP 帧 42 字节而非至少 64（抓包点在填充与 FCS 之上）；四次挥手只有三个报文（ACK 与 FIN 合并）；ping 之后 5 秒冒出一对单播 ARP（邻居表复查）。
