# 第 02 讲回顾讲义：二层交换与静态路由

> **课程导读**：同一个 `ping 不通`，可能是网桥没有把帧送到目标端口，也可能是路由选错了下一跳，还可能是请求已经到了、回复却回不来。这份讲义参照[第一讲回顾](network_review.md)，用第 02 讲的查表与抓包输出串起问题：**网桥看什么表，主机和路由器看什么表，一份数据在每一跳究竟改变了什么？** 最后用一次纸面故障诊断，把“猜原因”变成“找证据”。内容限于[第二讲](switching_routing.md)，不展开 Lab 1 的脚本实现任务。

## 十、判断改错

34. ● 判断下列说法是否正确；错误的要改成一句有条件、可核对的陈述，并指出原讲义的小节。

    - **a.** 网桥用帧的目的 MAC 学习“这个 MAC 在哪个端口后面”。
    - **b.** 未知单播需要泛洪，所以网桥会先把目的 MAC 改成广播地址。
    - **c.** 把接口加入 bridge 后，网关 IP 应继续配在桥端口上，bridge 只是一个名字。
    - **d.** `ip neigh flush all` 会同时清空邻居表、FDB 和路由表。
    - **e.** 同一张路由表里，`metric 1` 的 `/24` 一定能压过 `metric 100` 的 `/32`。
    - **f.** `ip route get` 返回了下一跳，就证明目的主机可达。
    - **g.** 无 NAT 的普通 IPv4 转发中，源/目的 IP 保持不变，TTL 与首部校验和可能改变。
    - **h.** r1 能回复发给自己接口地址的 ping，就证明 r1 已开启转发。
    - **i.** 在 r2 的入接口抓到 Echo Reply，就证明它已经被 r2 转发出去。
    - **j.** `ping` 输出的 TTL 反映回复到达时的剩余值；推算回程跳数还需要知道初始值。
    - **k.** 普通透明网桥不递减 IP TTL，所以 traceroute 不会为它单独显示一跳。
    - **l.** FDB 老化时间很长时，主机换端口之后一定要等老化结束，映射才会更新。

## 十一、从程序员的角度：第 02 讲给我们的启发

### 启发 1：不同的表回答不同的问题

路由表回答“下一步走向哪里”，邻居表回答“这个下一跳的链路地址是什么”，FDB 回答“这个 MAC 应该送到哪个桥端口”。它们都参与一次发送，却不能彼此替代。写程序也一样：服务发现、连接状态与任务队列是不同层面的状态。排查前先说清楚这张表的键和值，才能知道清缓存、改配置究竟改到了哪一层。

> **想一想**：看到下一跳邻居处于 `FAILED`，为什么反复修改目的网段的路由未必有用？你还需要检查哪个接口、哪个邻居的什么证据？

### 启发 2：局部决定不等于端到端成功

`ip route get` 能告诉我们本机准备怎样发送，却不验证后面的路由器是否转发，也不验证回复能回来。这和任务成功进入队列、请求成功写入套接字类似：完成了一步，不能当成整个业务完成。每一步的“成功”都应注明它保证了什么。

> **想一想**：给一个网络服务写健康检查时，“进程在运行”“端口能连接”“一次业务请求完整返回”各验证到哪里？

### 启发 3：请求与回复是两条独立的证据链

第八节中，对端已经收到请求并发出回复，源端却仍然超时。因此“没收到响应”不等于“对端没处理”。分布式程序遇到超时，既要查请求路径，也要查响应路径；若选择重试，还应考虑第一次操作可能已经执行。

> **想一想**：如果把 Echo Request 换成“给账户增加一次积分”的业务请求，回复丢失后直接重试会带来什么问题？应用需要保存什么标识来辨认重复请求？

### 启发 4：自动学习既要更新，也要遗忘

网桥根据源 MAC 学习端口，后续收到同一源从新端口发来的帧时，可以更新动态表项；老化处理的是长期没有刷新记录的情况。因此“更新映射”和“等待过期”是两条不同路径。缓存设计既要考虑多久忘记旧值，也要考虑新证据何时能覆盖旧值。

> **想一想**：主机迁移后一直沉默，与迁移后立刻发出一个帧，对交换机收敛有什么不同？这如何修正判断题 l？

### 启发 5：反例与对照比反复重试更有用

“关转发”和“删回程路由”在源端表现相近，但在右侧链路上的预测不同。找到一个能区分候选原因的观察点，比把同一条 ping 多跑十次更有效。调试程序也应先列出候选原因，再选能让它们产生不同结果的检查。

> **想一想**：题 29 中，哪一次观察最有区分力？如果没有权限到 r2 抓包，只能从 h1a 探测，你的结论需要保留哪些不确定性？

### 启发 6：让计算看见路径，而不只看见地址

同机架和跨机架的通信，对程序都可以是一次发送，但它们经过的链路和共享资源不同。本讲只能证明路径与转发行为，还没有测出容量、排队或作业完成时间。后续把这些指标补上，才能讨论“把任务放在哪里、让哪些数据少跨机架”。

> **想一想**：如果两项计算需要交换大量数据，仅知道两台主机都能 ping 通，够不够决定放置位置？还需要测哪些量？
