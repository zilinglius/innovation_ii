## 一、动态路由到底替我们做了什么

1. **40 个机架是 1560 条，41 个机架是 1640 条，增加 80 条。** 即 $40\times39=1560$、$41\times40=1640$；新增路由器要写 40 条，原有 40 台各加 1 条。这个模型排除了汇总、默认路由与不同拓扑的配置方式，因此只能说明本题逐目的配置的扩展代价。动态协议减少的是手工维护远端可达性的负担，地址规划与策略配置仍然存在。→ 1.1 节

2. **Hello 接收、最短路计算、下发路由属于控制平面；逐包减 TTL 和转发属于数据平面。** 稳态仍有 Hello、刷新与定时器处理，控制平面并非只在拓扑变化时运行。下面的路由状态链与业务包链应分开读。→ 1.3、3.3、5.1 节

    ```mermaid
    %% routing-review:planes_answer
    flowchart LR
        O["ospfd · 协议与 SPF"] --> Z["zebra · RIB 选优"] -->|"netlink 安装路由"| F["内核 FIB"]
        P["业务 IP 包"] --> K["内核查表并转发"]
        F -.->|"供查询"| K
    ```

    *图 1：上排传递路由状态，下排处理业务 IP 包；虚线表示查表依赖。包不需要逐个进入 ospfd 或 zebra；内核接口事件的反向通知为简洁未画。*

3. 依次是 **“我到各目的地有多远”“我的邻接、网段及链路代价”“经过的 AS 与路径属性”**。IGP 服务于一个 AS 内部，EGP 处理 AS 之间的可达性与策略。AS 是管理与策略边界，不是某种固定物理规模。动态路由仍要配置地址、启用接口、区域或对等体、策略等；“自动算路”不等于“零配置”。→ 1.4–1.5、4.3–4.4 节

## 二、只听邻居说距离，能算出路吗

4. r1 的表如下；“未知”可视为本推演中的无穷，RIP 用 16 表示不可达。→ 2.1–2.3 节

    | 轮次 | LAN1 | LAN2 | LAN3 |
    | --- | --- | --- | --- |
    | 0 | 1，直连 | 未知 | 未知 |
    | 1 | 1，直连 | 2，经 r2 | 未知 |
    | 2 | 1，直连 | 2，经 r2 | 3，经 r2 |

    ```mermaid
    %% routing-review:dv_rounds
    flowchart LR
        A["第 0 轮 · r3 知道 LAN3=1"] -->|"r2 加 1"| B["第 1 轮 · r2 知道 LAN3=2"]
        B -->|"r1 再加 1"| C["第 2 轮 · r1 知道 LAN3=3"]
    ```

    *图 2：只追踪 LAN3 的信息向左传播；箭头是跨一轮的知识传递，不是数据包转发。LAN1、LAN2 的对称传播省略。*

    第一轮 r2 才从 r3 学到 LAN3；第二轮 r1 才能使用 r2 的新向量。同步轮次是计算模型，实际更新受启动时机、触发更新、抖动与丢包影响，不能把两轮机械换成恰好 60 秒。

5. **选择 r3，总距离 5。** 更新式为 $D_x(y)=\min_{v\in N(x)}\{c(x,v)+D_v(y)\}$。经 r2 是 $2+5=7$，经 r3 是 $4+1=5$；r1 只需邻居的距离和本地到邻居的代价，不知道 X 的完整路径。这个便利也带来信息来源不透明的问题。→ 2.1 节

6. **r1 先变为 3 经 r2；r2 再变为 4 经 r1；下一次 r2 宣告 4 后，r1 变为 5，经 r2 的 r3 也可变为 5。** r2 的现用下一跳就是 r1，当这个来源报告变差时仍要更新，否则会永久保留已经失效的低代价。问题不是“接受了坏消息”，而是 r1 把依赖自己的旧消息误当成另一条独立出路。TTL 只能限制单个业务包在环内的寿命，不会更正错误向量。→ 2.4 节

7. **水平分割是不向学习接口回报；毒性逆转是向该接口回报不可达 16；触发更新是不等下一次周期更新便安排发送变化。** 前两者限制信息如何回传，后者改变传播时机。它们不能保证一般多节点环永远不出现；也不能把 RIP 的局限推广成所有距离向量协议都无法设计无环条件。→ 2.5–2.6 节

    ```mermaid
    %% routing-review:poison_answer
    flowchart LR
        A["r1 · LAN1 的来源"] -->|"LAN1=1"| B["r2 · 学到 LAN1=2 via r1"]
        B -.->|"水平分割：省略 LAN1"| A
        B -.->|"毒性逆转：LAN1=16"| A
    ```

    *图 3：后两条虚线是两种不同策略的对照，不表示同时发送两个回复；箭头均为通告方向。毒性逆转的关键是“向学习来源反向宣告”，不能只看 metric 是否为 16。*

## 三、抓到的 RIP 报文，真是“整张表”吗

8. **`224.0.0.9` 是 RIPv2 组播地址，520 是此处 UDP 源、目的端口。** `metric:1` 是发送者 r1 所宣告的距离；r2 经 cost=1 的接口学到后是 2。44 字节为本例 RIP 报文的 $4+2\times20$ 字节，不含 UDP 与 IP 首部。不能把接收者计算后的 2 反写成这份抓包实际包含的值。→ 2.3、6.11 节

9. **这与水平分割一致。** r1 不把从 r2 学来的路由再沿同一接口报回 r2；“周期全表”也受出接口的通告规则与分包限制，并不保证每个报文包含 RIB 中每条路由。某个前缀没在这份通告出现，只说明它没被这份消息携带，不能单独推出不可达；还需结合协议状态、完整更新与超时。→ 2.5、6.11 节

10. **不一定。** 故障后把失效路由标成 16 并向其他邻居发送，可以是路由毒化／撤销；毒性逆转特指把从某来源学来的路由向该来源宣告为 16。原讲义 r1 在 r1–r3 上宣布失效目的地的场景，不能仅凭 16 就命名为毒性逆转。30 秒为周期更新，180 秒为路由超时，120 秒为标记不可达后的垃圾回收期；这些是 RIP 规范口径，不保证某次恢复恰好发生在这些时刻。触发更新还受限速和合并影响，不承诺毫秒每跳。→ 2.3–2.5、6.11 节；补充依据：[RFC 2453 §3.10.1](https://www.rfc-editor.org/rfc/rfc2453.html#section-3.10.1)规定发送触发更新后的 1–5 秒随机抑制定时器。

## 四、Hello 已经收到了，为什么还不是 Full

11. **收到 Hello 只说明自己听见对方，故可停在 Init。第三条由 r1 发出、列表含 r2 的 Router ID，因此 r2 可以确认 r1 也听见过自己，进入 2-Way。** 证据是对方报文中的邻居列表；源 IP 只指出本链路报文来自哪里。r1 是否也能确认双向，要看 r2 发来的 Hello 是否包含 `1.1.1.1`，不能从第三条反推。→ 3.2、6.5 节

12. **DBD＝摘要，LS Request＝索要缺项，LS Update＝完整 LSA，LS Ack＝确认。** Hello 解决邻居存活与双向发现，数据库同步还要交换、比较并补齐信息；LSA 是被描述、比较的状态对象，LS Update 是承载一个或多个 LSA 的 OSPF 报文。→ 3.2–3.4、3.6 节

    ```mermaid
    %% routing-review:hello_answer
    sequenceDiagram
        participant A as r1
        participant B as r2
        A->>B: Hello · 列表含 r2
        B->>A: Hello · 列表含 r1
        Note over A,B: 确认双向；点到点邻接继续同步
        A->>B: DBD · LSA 摘要
        B->>A: DBD · LSA 摘要
        B->>A: LS Request · 请求缺少或较新的 LSA
        A->>B: LS Update · 完整 LSA
        B-->>A: LS Ack · 确认
        Note over A,B: 同步完成后 Full
    ```

    *图 4：数据库同步的逻辑顺序；省略 ExStart 主从协商、重复交换和反向索要等细节，不表示真实握手固定只有七个报文。示例假设 r2 缺少的 LSA 由 r1 提供。*

13. **使用 `proto ospf`，因为 OSPFv2 在本例直接封装于 IP 协议号 89，并没有 UDP 端口 89。** `Full/-` 表示已完全邻接，点到点链路没有 DR/BDR 角色；`passive-interface br1` 不在该接口建立 OSPF 邻居，但仍可把该接口网段纳入通告。点到点类型省去广播网的 DR/BDR 选举；在普通广播网中，两个 DROther 可以正常停在 2-Way，并非所有邻居对都应达到 Full。这里的 `ttl=1` 是本实验链路内报文，不应推广到 OSPF 所有特殊场景。→ 3.2、3.6、6.4–6.5 节

14. **Router ID 是 OSPF 身份标识，`10.0.12.2` 是这条链路上的邻居地址；写法相似不代表用途相同。** 本例收到下一次有效 Hello 后，失效计时重新按配置的 40 秒开始；展示值随查询时刻变化。`-N r1` 选择 r1 这套 FRR 的 pathspace，省略后可能连接默认的全局实例，结果不能当成 r1 的状态。→ 3.2、5.4、6.5 节

## 五、地图相同，为什么 Age 不同

15. **同类型、同 Link State ID、同发布者先确定 LSA 身份；相同 Seq#、CkSum 支持两处保存同一版本。** Age 是随存储与传播增长的年龄，不要求同一瞬间各地逐字相同；只看一行摘要也不等于完成整份数据库内容校验。OSPF 的区域拓扑数据库以 Area 为范围，不能要求整个多区域 AS 的所有路由器保存相同的区域地图。→ 3.3–3.4、3.6、6.6 节

16. **5＝2 条点到点邻接＋3 个 stub 网段。** r1 邻接 r2、r3，并描述 LAN1、r1–r2 的 /30、r1–r3 的 /30；`Link count` 不是邻居数。序列号还会因刷新、状态演进等原因更新，起点与生命周期也需结合背景判断，因此不能从 `0x80000005` 单独反推出“四次链路故障”。→ 3.3、6.5–6.6 节

17. **r3 已有该版本，无需把同一状态再次扩散；确认与重传队列仍按协议处理。** 同一 LSA 由 LS type、Link State ID、Advertising Router 识别。完整 OSPF 的新旧比较还使用 checksum、MaxAge 及年龄差规则，不是仅凭“seq 一样”就随意判定完全相同；下图按题设已经完成合法性与版本判断后的语义分支绘制。→ 3.3–3.4 节；边界依据：[RFC 2328 §13.1](https://www.rfc-editor.org/rfc/rfc2328.html#section-13.1)。

    ```mermaid
    %% routing-review:flood_answer
    flowchart TD
        R["接收合法 LSA · 识别身份并比较版本"] --> N["本地没有或收到更新版本"]
        R --> S["与本地版本相同"]
        R --> O["收到较旧版本"]
        N --> I["装入 LSDB · 按规则泛洪 · 安排 SPF"]
        S --> D["不重复扩散 · 按规则处理确认"]
        O --> B["按规则用本地较新副本纠正对方"]
    ```

    *图 5：LSA 处理的语义分支，省略完整 RFC 状态机中的节流、确认细节与特殊状态。这里的“泛洪”是向符合条件的邻接重新发送，包含去重，不等同于以太网帧的盲目复制。*

18. **发送方保留待确认状态，未获确认时可重传；重复到达仍需按版本与确认规则处理。** 本例接口 `Retransmit 5` 是重传间隔的观察值。稳态仍可能刷新 LSA；本讲介绍的正常刷新时间为 1800 秒，MaxAge 为 3600 秒。地图一致与业务通过之间还隔着 SPF、选优、FIB 安装及实际转发条件，收敛过程也可能有暂时不一致。→ 3.3–3.4、3.6、6.7 节

## 六、会算最短距离，还要会找第一跳

19. **到 r2、r3 的距离都是 10，到 LAN2 是 20。** 一种合法的 Dijkstra 顺序如下；并列时先取 r3 也正确。→ 3.5 节

    | 步骤 | 已确定 | 候选与松弛结果 |
    | --- | --- | --- |
    | 起点 | r1，0 | r2=10、r3=10 |
    | 确定 r2 | r1、r2 | 经 r2 到 r3 为 20，不优于已有 10 |
    | 确定 r3 | r1、r2、r3 | 经 r3 到 r2 为 20，不改结果 |

    LAN2 是前缀，不是 r2 顶点本身；还要加 r2 描述的 LAN2 stub cost 10，故为 $10+10=20$。算法代价没有毫秒单位，不等于测得的路径时延。

20. **经 r2：`via 10.0.12.2 dev r1-r2`；经 r3：`via 10.0.13.2 dev r1-r3`。** 两条到 `10.0.23.0/30` 的代价均为 $10+10=20$，第二个 10 来自该 /30 在相应路由器 LSA 中的 stub 描述。基线到 LAN2 的直达路线为 20，经 r3 则为 30，所以只有前者最短。ECMP 是针对特定目的前缀的结果，不能从一条路由推广到所有目的地。→ 3.5、5.3、6.7 节

21. **两端 cost 都改为 20 后，r1 到 LAN2 的直达和绕行都是 30。** 直达 $20+10=30$，绕行 $10+10+10=30$。若只改 r1 出方向，r1 仍有这两条等价路；r2 回 LAN1 的直接路径仍为 $10+10=20$，绕 r3 为 30，因此 r2 不出现对应 ECMP。→ 3.5、6.10 节

    ```mermaid
    %% routing-review:cost_answer
    flowchart LR
        subgraph A["基线：r1 到 LAN2"]
            A1((r1)) -->|"10"| A2((r2)) -->|"10"| AL["LAN2"]
            A1 -.->|"10"| A3((r3)) -.->|"10"| A2
        end
        subgraph B["两端直连 cost=20：r1 到 LAN2"]
            B1((r1)) -->|"20"| B2((r2)) -->|"10"| BL["LAN2"]
            B1 -->|"10"| B3((r3)) -->|"10"| B2
        end
    ```

    *图 6：基线直达 20、绕行 30，虚线是未选候选；对照直达与绕行均为 30，两条都是可选最短路径。只展示 r1 出发的计算方向与前缀末段，不表示每个业务包复制到两条路径，也不承诺回程对称。*

22. **相同地图、不同根，会产生不同的最短路径树与下一跳。** 写表还需要“目的前缀 → 一个或多个首跳”，并把首跳 Router ID 映射为本地出接口和可达的下一跳 IP；只存距离无法回答从哪个口发。保留等代价首跳集合才能表达本题的 ECMP；也要知道哪些是本地直连前缀，避免把算法结果不加区分地覆盖直连路由。→ 3.5、5.1、6.7 节

## 七、两个 20，真的是同一个意思吗

23. **`O`＝OSPF，`C`＝直连，`>`＝被选中，`*`＝FIB 路由；`[110/30]`＝管理距离 110／OSPF cost 30。** 直连来源在本例管理距离为 0，胜过 OSPF 的 110，因此本地 LAN1 的 `C>*` 生效。Linux `metric 20` 属于内核选路优先级，FRR 在本例统一使用 20 写入路由，并非 OSPF cost 或管理距离；其不变不代表更新失败。→ 5.1–5.2、6.7、6.10 节；实现依据：[FRR 8.4 Zebra](https://docs.frrouting.org/en/stable-8.4/zebra.html#route-selection)。

    ```mermaid
    %% routing-review:metrics_answer
    flowchart LR
        A["基线 RIB · 110 / 20"] --> B["基线 FIB · metric 20 · 一个下一跳"]
        C["改 cost 后 RIB · 110 / 30"] --> D["改 cost 后 FIB · metric 20 · 两个下一跳"]
    ```

    *图 7：两层度量并列比较。RIB 方括号内后一个数是 OSPF cost；内核 metric 是另一套选择字段。应同时核对来源、下一跳与接口，不能只比较数值是否一样。*

24. 空白依次填 **zebra、netlink**。ospfd 管 OSPF 计算，zebra 汇总各协议候选并选优、安排下发，Linux 内核实际处理业务包。原实验由 `ip route add` 留下的同前缀路由可能作为 kernel 来源优先于 OSPF 候选；该手工路由的内核 metric 也不同于 FRR 安装的 metric。应分别看 FRR `show ip route` 的来源／选中标记和内核表，确认谁生效。`proto ospf` 是来源标签，也不能脱离上下文当成无法人为设置的证明。→ 5.1–5.2、6.2–6.3 节

25. **不能断言 ECMP 失败；样本少时哈希可以碰撞。** 本题普通 IPv4 下策略 0 按第三层信息选择，同一对源／目的主机通常落到同一路；策略 1 把传输层字段纳入，不同 TCP 源端口才有机会落到不同下一跳。等权描述分摊机会，不保证小样本恰好均分，更不保证字节负载均匀。保持路由、下一跳集合和哈希设置稳定是讨论流内路径稳定的前提，故障换路会改变映射。→ 5.3、6.10 节；字段范围参见 [Linux IP Sysctl](https://docs.kernel.org/networking/ip-sysctl.html#fib-multipath-hash-policy-integer)。

    ```mermaid
    %% routing-review:hash_answer
    flowchart LR
        F["连接的源/目的地址与端口"] --> H["策略 1 · 哈希选择"]
        H -->|"候选 A"| A["via 10.0.12.2 · r1-r2"]
        H -->|"候选 B"| B["via 10.0.13.2 · r1-r3"]
    ```

    *图 8：每次选择一个下一跳；两条箭头是候选分支，不是报文复制。不同连接可能碰撞到同一分支，同一连接也不应被解释成逐包交替轮转。*

26. **`route get` 证明本机对给定输入的查表选择，不发送该业务，也不检查远端与回程。** traceroute 观察探测包触发的各跳响应；传统 UDP 探测端口变化后，五元组哈希可能改变所走分支，因此不能机械拼接每行第一个地址作为某条 TCP 连接的轨迹。要验证真实流量，可在 r1 两条出接口及相关后续接口抓包，结合五元组、TCP 序列号或 ICMP 标识／序号和时间对齐；还要说明观察窗口内路由是否稳定。→ 5.3、6.7、6.10 节

## 八、同一条备用路，为什么这次等了三十多秒

27. **这组探针没有最终丢失；一秒后的快照说明此时 r1 已安装备用下一跳。** 不能把最大 RTT 1.461 ms 直接当成收敛时间，它还包括传播、处理、调度与排队，且没有证据表明它恰是跨越切换的那一个包。0.2 秒采样也可能漏掉短中断；没有故障时刻、逐包时间与路由事件对齐，就不能从这几个摘要精确测出中断长度或全网收敛时刻。→ 3.7、6.8 节；这里收紧了样例的推论边界。

28. **最终缺失 $300-127=173$ 个回复，$173\times0.2=34.6$ 秒是按采样间隔折算的中断量级。** 16–188 含首尾正好 173 个序号；这仍是往返探针的观测，不能独立分离去程、回程以及每段处理时间。`no answer yet` 是当时尚未收到，迟到回复仍可能随后出现，因此要结合最终统计与逐包记录。→ 3.7、6.9 节

    ```mermaid
    %% routing-review:timer_answer
    flowchart LR
        H["最后一次有效 Hello · tH"] -->|"已过去 δ 秒"| F["故障发生 · tF"]
        F -->|"检测等待约 40−δ 秒"| D["Dead 到期 · tH+40"]
        D --> R["传播 / SPF / 安装 / 业务恢复"]
    ```

    *图 9：时间线不是按比例绘制。Dead 从最后有效 Hello 计时，故障不是重置计时器的事件；34.6 秒是原探针统计的折算值，不能据此精确反推图中每个阶段。*

    若此前 Hello 稳定每 10 秒到达、没有调度或报文异常，故障时剩余 Dead 大约在 30–40 秒之间，所以三十多秒并不违背 40 秒配置。实际业务还要等待后续传播、计算、安装与双向路径可用。

29. 证据链应跨越协议状态和真实业务，而不是把一次 ping 当成全部阶段的计时器。→ 3.7、5.1、6.8–6.9 节

    | 阶段 | 可记录的证据 | 判断边界 |
    | --- | --- | --- |
    | 故障与检测 | 注入时刻、接口载波事件、最后 Hello、邻居状态变化 | 接口 UP 不等于路径健康；日志记录时刻也有误差 |
    | 传播 | 不同节点收到新 LSA 的身份、版本和时间 | 收到一条不等于全网同步 |
    | 计算 | SPF 触发、完成及候选首跳变化 | 得到候选不等于被选中 |
    | 安装 | RIB 标记、内核路由事件与 FIB 快照 | FIB 改好不等于回程或过滤正常 |
    | 业务恢复 | 带序号的真实探针、业务抓包与接收记录 | 明确单向／往返、采样间隔与成功标准 |

    Hello/Dead 调为 1/3 秒只能在满足相应 Hello 失效检测条件时缩短等待；仍需备用路径、邻接与配置一致、计算和安装能及时完成。只影响业务、不影响 Hello 的故障可能不触发这套检测。更短计时带来更多处理、更易受丢包或调度延迟影响，可能误判并反复重算；不能承诺所有故障 3 秒恢复。

30. **r3 的本地邻接没有改变，所以自己的 Router-LSA 可保持原版本；但它保存的 r1、r2 的 LSA 已改变，输入地图变化就需要重新计算。** r1、r2 各少了一条点到点邻接与一个 /30 stub，Link count 从 5 到 3。序列号一次实验涨了 2 是记录到的状态演进，不是“一次故障必须加 2”的规则。接口恢复后还要重新发现／确认双向、同步并安装路径；应查邻居、路由及业务恢复，不靠固定睡眠时间保证成功。→ 3.3–3.5、6.8 节

## 九、AS_PATH 更长，为什么反而选它

31. **普通 eBGP 防环规则会排除含本 AS 65001 的路径；选路题选甲。** 甲的 LOCAL_PREF 200 高于乙的 100，在题设比较顺序中先胜出，不再由更短 AS_PATH 翻盘。这是受题设限制的教学顺序，不是每个厂商全部选路条件的完整列表。AS_PATH 中的 AS 顺序也不是 AS 内部经过的每台路由器清单。→ 4.3–4.5 节；参考 [RFC 4271 §9.1](https://www.rfc-editor.org/rfc/rfc4271.html#section-9.1)。

    ```mermaid
    %% routing-review:bgp_answer
    flowchart LR
        A["甲 · LOCAL_PREF 200 · AS_PATH 长度 3"] --> C["先比较本 AS 偏好"]
        B["乙 · LOCAL_PREF 100 · AS_PATH 长度 1"] --> C
        C --> W["选择甲 · 不再比路径长短"]
    ```

    *图 10：两候选均合法、NEXT_HOP 可达，其他更早的本地优先条件相同。路径长度是本题 AS_SEQUENCE 中的 AS 个数，不是 IP 跳数或毫秒时延。*

32. **TCP，服务端口 179。** 会话先交换按策略允许通告的路由，之后 UPDATE 携带增量宣告或撤销；依靠 TCP 在存活会话内提供有序可靠字节流，无须用周期全表弥补普通传输丢失。可靠传输不证明宣告归属真实，也不解决策略冲突或路径探索，不能保证任意策略组合快速收敛。→ 4.4、4.6 节

33. **难点是管理与策略边界、拓扑披露，以及状态传播和计算的扩展成本。** 不应把原因简化成某个固定前缀数量“一定装不下内存”；不同 AS 并不愿意共享内部地图，也不服从统一最短路目标。数据中心可给不同设备分配私有 ASN，使 eBGP 在一个组织内部的多个 AS 之间运行，并不矛盾。其作用范围取决于拓扑、汇总与导出策略；撤销也可能逐跳传播，不能说 BGP 故障永远只影响直连邻居。→ 1.5、4.2、4.7 节；工程背景：[RFC 7938](https://www.rfc-editor.org/rfc/rfc7938.html)。

## 十、把“路由没通”拆成可检查的问题

34. 四组命令分别观察**邻接状态、LSDB、RIB 与 FIB、针对给定包输入的本机选路**。还缺真实业务流量的证据：在 r1 的 `r1-r3` 与 r3 的 `r3-r2` 等观察点核对同流／同包，在 h2a 确认到达，需往返成功时再检查回程。必须把接口、方向、报文标识和路由稳定窗口一起记录；不能拿不同时间的两份无关流量当成一条路径。→ 5.1、6.5–6.10 节

## 十二、从程序员视角再想一步

### 1. “我有路”是一份需要过期的缓存

参考思路：路由是带来源、有效期与版本的状态，不是永久事实。邻居失效时要撤销依赖它的结果，收到旧消息时不能让已经过期的状态随意复活。服务发现缓存也需要区分“从未知道”“仍有效”“已失效”，但不能直接照搬 RIP 的数字作为业务系统的超时。

### 2. 双向握手在证明什么

参考思路：r2 在 r1 的 Hello 列表里看见自己，是对“r1 曾听到 r2”的明确反馈；配合自己收到 r1 的消息，构成双向发现。它没有证明数据库同步、FIB 安装、应用端口或端到端业务可用。为每种成功状态写出准确含义，比只用一个 `connected=true` 更容易诊断。

### 3. 重试必须配合去重

参考思路：重试提高丢包环境中的送达机会，去重阻止重复状态在环上反复扩散。只重试可能造成重复处理和消息放大；只去重不能补回从未到达的更新。确认也可能丢失，接收重复消息时仍须有适当的确认处理。OSPF 的完整规则与 Lab 2 的简化可靠泛洪不是同一套线协议。

### 4. 算对了，不等于生效了

参考思路：记录 LSDB 版本、SPF 输入与首跳集合、选路胜出来源、安装请求及结果，再用内核表和业务报文核验。每个边界都能发生“上游成功、下游未生效”，如候选被更优先来源压住、安装报错、过滤丢包。一个总开关式的“路由正常”日志不足以定位这些问题。

### 5. 超时是判断，不是事实本身

参考思路：超时是一种在有限信息下的失效判断。除计时器长度，还要记录消息丢失、事件处理延迟和误判后的恢复成本。更短超时可能更快发现真故障，也可能在负载高时来回判死、重连、重算；“更快”须结合误判率与业务中断衡量。

### 6. 让计算看见网络，从区分指标开始

参考思路：FIB 验证候选路径，抓包验证连接实际使用的路径，发送／接收计数验证有效吞吐，应用起止记录验证作业完成时间（JCT）。同时固定数据量、并发关系、测量窗口和背景负载；路径数变多只增加利用容量的可能，不保证某次作业一定更早结束。

本讲已完成协议与证据的回顾；[第四讲](link_state_router.md)把这些动作拆成程序事件，[Lab 2](../experiments/02/README.md)再按 LSR-lite v1 实现、测量并解释。完整 OSPF、FRR 样例与学生简化协议应分别标识，不能要求学生复现完全相同的定时器或丢包数字。
