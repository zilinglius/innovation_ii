## 一、网桥的表里为什么没有 IP

1. **`master br1` 表示接口属于 br1；`state forwarding` 表示这个桥端口处于二层转发状态。** 后者是桥端口状态，不是 `net.ipv4.ip_forward` 的取值。桥接处理同一广播域内的帧；IPv4 转发处理目的地不在本机、需要路由到另一接口的包。应在 r1 内另外读取 `sysctl net.ipv4.ip_forward`，不能由桥端口的状态推断它已经打开。→ 2.1、2.4、4.1 节

2. **br1 根据收到帧的源 MAC 与入端口自动学习。** 第二行表示 h1a 的 `12:d2:96:8e:ba:65` 位于 `r1-h1a` 后面，第三行表示 h1b 的 `d2:29:2a:88:ce:ee` 位于 `r1-h1b` 后面。收到 h1a 发来的帧，说明“去这个源 MAC 可以走入端口”；转发当前帧时再查它的**目的 MAC**。学习与查找使用的是两个不同字段。→ 1.3、2.4、6.6 节

3. **本例第一行是 r1 的桥端口 `r1-h1a` 自身的本地 MAC 条目。** `permanent` 表明它不是靠远端主机流量学习、等待老化的动态记录。它与同端口后面 h1a 的动态记录含义不同，不能数成两台远端主机。目的 MAC 命中本地条目时，帧交给本机相应协议处理；命中远端动态条目时，按端口转发。是否进一步送入 IPv4、ARP 等处理，还取决于帧类型。→ 2.4 节、模块七思考题 3

4. 三张表各回答一件事。在本讲无 VLAN、普通 IPv4 以太网的范围内：→ 1.3、2.4、3.1–3.2、4.2 节

    | 表 | 键与结果 | r1 内的查看方法 |
    | --- | --- | --- |
    | FDB | MAC → 桥端口；也包含本地投递条目 | `sudo ip netns exec r1 bridge fdb show br br1` |
    | 邻居表（Neighbor Table） | 下一跳 IP 与接口 → MAC、邻居状态 | `sudo ip -n r1 neigh show` |
    | 路由表 | 目的前缀 → 下一跳与出接口 | `sudo ip -n r1 route show` |

    FDB 转发的是以太网帧，查询依据是 MAC，不需要用 IP 作为查找键。不能用邻居表里的 IP–MAC 对应关系代替 FDB 的 MAC–端口对应关系。

## 二、旁观者 h1b 为什么只看到一个帧

5. **h1a 在询问网关 `10.0.1.1` 的 MAC。** 以太网目的地址是广播地址 `ff:ff:ff:ff:ff:ff`，所以 br1 把它复制给其他转发端口；ARP 的目标协议地址则是 `10.0.1.1`。h1b 的地址是 `10.0.1.12`，在本题未配置代理 ARP 的条件下，它不是被询问者，不应回答自己拥有网关地址。“广播接收者”不等于“ARP 问题的目标主机”。→ 1.3、6.7 节

6. **请求从 `r1-h1a` 进入时，网桥学到 `12:d2:96:8e:ba:65 → r1-h1a`。** 网关构造 ARP Reply 时，从请求里知道 h1a 的 MAC；网桥随后根据已学到的目的 MAC 表项把回复送到 `r1-h1a`，无需复制到 `r1-h1b`。这里既有 ARP 报文中的地址信息，也有 FDB 的端口信息，两者作用不同。→ 1.3、6.7 节

7. **`ip neigh flush all` 操作邻居表，不会同时清空 FDB 或路由表。** 即使请求之前 h1a 的动态 FDB 表项不存在，正常开启学习的网桥也会在收到广播请求时先学到它；等 Reply 返回时，表里已经有目的 MAC 对应端口。因此“起初 FDB 为空”不意味着这次 Reply 必定泛洪。若关闭端口学习或改了桥的转发策略，须按实际条件重判；那不是本题基线。→ 1.3、2.4、6.7 节

8. **在本讲端口允许未知单播泛洪的条件下，h1b 可以收到该帧的副本。** 网桥复制帧，但不把目的 MAC 改成广播地址：未知单播仍然是单播，只是网桥尚不知道它在哪个端口。混杂模式让抓包程序看见送到本接口、即使目的 MAC 不属于自己的帧；它不能要求交换机把其他端口的已知单播也送来。多看到 IPv6 背景报文只说明抓包窗口还有别的流量，应按 EtherType、地址和协议区分，不能据此推翻本次 ARP 广播与 ICMP 定向转发的结论。→ 1.3–1.5、6.7 节

## 三、三条路由只手工配了一条

9. **第一、三行是内核生成的直连路由，第二行是手工配置的静态路由。** `proto kernel` 标识前两者的来源；在本实验中，给启用的接口配好地址即可得到对应的网段路由。第二行中 `10.0.2.0/24` 是目的前缀，`via 10.0.12.2` 是下一跳，`dev r1-r2` 是出接口。这只描述 **r1 当前这一步**：下一台 r2 还要查自己的表。路由项没有把 h1a 到 h2a 的全部设备依次列出。→ 3.1–3.2、5.2 节

10. **应解析下一跳 `10.0.12.2`。** r1 发出的新帧目的 MAC 是 r2 的 `r2-r1` 接口 MAC；包的目的 IP 仍是最终接收端 `10.0.2.11`。若已有可用邻居记录，可以直接用其 MAC 发送，不必每个包都先发 ARP；邻居状态机后续是否探测是另一件事。只有在最后一跳由 r2 直接交付给 h2a 时，才解析 h2a 自己的 IP。→ 3.1、5.4 节

11. **`src` 是本机主动发包时的首选源地址提示，不是给转发包做源地址改写。** 因而无 NAT 时，经过 r1 的包仍以 `10.0.1.11` 为源 IP。即使路由表完整，`ip_forward=0` 也不会替 h1a 转发到 h2a。要使包实际通过，还需打开 IPv4 转发，并满足接口、邻居解析及过滤等条件；查表与抓取出接口上的真实业务包验证的是不同层次。→ 3.2、4.1、5.4 节

## 四、最长前缀：为什么不走默认网关

12. 最长前缀匹配（Longest Prefix Match）比较的是**匹配目的地址的前缀位数**，不是表中行的位置。→ 3.3 节

    | 目的地址 | 匹配的全部前缀 | 胜出的前缀 | 下一跳 |
    | --- | --- | --- | --- |
    | `10.0.2.11` | `0.0.0.0/0`、`10.0.2.0/24` | `/24` | `10.0.1.1` |
    | `10.0.2.12` | `0.0.0.0/0`、`10.0.2.0/24`、`10.0.2.12/32` | `/32` | `10.0.1.12` |
    | `10.9.9.9` | `0.0.0.0/0` | `/0` | `10.0.1.1` |

    `/32` 约束全部 32 位，`/24` 约束前 24 位；默认路由 `/0` 不约束任何位，是没有更具体匹配时的兜底。本例中的 `10.0.1.0/24` 直连项不匹配这三个目的地址，它使两个下一跳可在本链路上解析。

13. **仍选 `/32`，不会因为 `/24` 的 metric 较小而改选它。** 本题在同一张已选路由表中先按最长前缀匹配；只有前缀具体程度相同的可比较候选项，才继续比较 metric 等优先级条件。不能跨不同长度的匹配前缀直接挑最小 metric。→ 3.2–3.3 节

14. **查询成功只能说明本机这次选路得到结果，不能证明目的主机可达。** `ip route get` 不发送这次业务包，不验证 h1b 是否开转发，也不检查回程。题设故意把 `/32` 指向普通主机 h1b，所以它是“选中了”与“能走通”分离的例子。在题设路由保持安装的情况下，一次 ping 超时或下一跳不能转发不会让内核自动撤销 `/32`、改用 `/24`；需管理员或相应路由管理机制改变路由。→ 3.3–3.5 节；工具依据见文末 `ip-route` 手册

15. **删除对照用的 `/32` 和 `/24`，保留原直连与默认路由。** 以下命令只适用于第四节那两条临时路由确实存在的阶段 B；删除已不存在的项会报错，应先查表而不是把所有错误忽略。→ 3.3、3.5、6.8 节

    ```bash
    # 1. 撤销两条临时选路对照项
    sudo ip -n h1a route del 10.0.2.12/32 via 10.0.1.12
    sudo ip -n h1a route del 10.0.2.0/24 via 10.0.1.1

    # 2. 检查恢复后的两次选路
    sudo ip netns exec h1a ip route get 10.0.1.12
    sudo ip netns exec h1a ip route get 10.0.2.12
    ```

    预期的关键字段如下，属于按题设推演，省略 `uid` 与可能出现的附加行；不是本次新增实测。

    ```text
    10.0.1.12 dev h1a-r1 src 10.0.1.11
    10.0.2.12 via 10.0.1.1 dev h1a-r1 src 10.0.1.11
    ```

    前者匹配 `10.0.1.0/24` 直连项；后者匹配默认路由。若连默认路由也删除，跨机架目标就没有匹配项，不能恢复原先的通信。

## 五、三条链路：同一个 IP 包换了三个“信封”

16. 三行属于**阶段 A**，逐跳字段如下。→ 3.1、5.1、5.4 节

    | 链路 | 发送接口 → 接收接口 | 源 MAC | 目的 MAC | 源 IP | 目的 IP |
    | --- | --- | --- | --- | --- | --- |
    | 1 | h1a:`h1a-r1` → r1:`r1-h1a` | `12:d2:96:8e:ba:65` | `f2:b7:b4:06:2b:0e` | `10.0.1.11` | `10.0.2.11` |
    | 2 | r1:`r1-r2` → r2:`r2-r1` | `66:35:06:b2:3e:3b` | `ea:8b:7b:b7:a4:4f` | `10.0.1.11` | `10.0.2.11` |
    | 3 | r2:`r2-h2a` → h2a:`h2a-r2` | `82:e2:98:2d:f9:18` | `e2:f5:08:50:cd:51` | `10.0.1.11` | `10.0.2.11` |

    MAC 描述当前链路上的交付对象，IP 描述这份数据最终要到哪里。第一段先把帧交给 r1，不等于把包的最终目的地址改成 r1；否则 r1 就失去了要把包转发到 h2a 的信息。

17. **这是三条链路分别发起的 ARP，不是一个广播穿过两台路由器。** `who-has` 依次询问 `10.0.1.1`、`10.0.12.2`、`10.0.2.11`，`tell` 依次对应各链路的发起接口地址。前两跳解析网关，最后一跳的目的主机就在直连网段上，下一跳才等于最终目的地。普通路由器不会把 ARP 广播当作 IP 包路由到另一个广播域。→ 1.4、3.1、5.4 节

18. **r1、r2 各转发一次，请求 TTL 从 64 变成 63，再变成 62。** 每次改动 TTL 都需要相应更新 IPv4 首部校验和，二层源/目的 MAC 则随新链路重新封装。无 NAT、未分片、没有其他改写的本例中，源/目的 IP 保持不变。若中间只是普通透明网桥，桥接动作不改源/目的 MAC，也不递减 IP TTL，因此不会因这次桥接而更新 IPv4 首部校验和。→ 1.5、4.3、5.4 节

19. **不能只靠省略后的三行或 IPv4 Identification 唯一认定是同一请求。** IPv4 ID 可以重复；同一对主机也可能短时间内连续发送多个请求。应结合源/目的 IP、协议、ICMP 类型、Echo 标识符与序号、接近的捕获时间，必要时再比较载荷；同时检查 MAC 属于对应链路、TTL 与路由转发次数相符。IPv4 ID 可以作为辅助字段，但不应单独承担全局唯一标识的角色。讲评时把原讲义“id 相同说明是同一个包”理解为受控实验窗口中的简写，不能推广成任意抓包的充分条件。→ 5.4 节；边界补充见 RFC 6864

## 六、同一块网卡，为什么发给不同的 MAC

20. **出接口相同，下一跳仍可能不同。** 两条决策链为：→ 3.1、6.8 节

    | 最终目的 IP | 匹配结果 | 邻居解析对象 | 以太网目的 MAC |
    | --- | --- | --- | --- |
    | `10.0.1.12` | 直连 `10.0.1.0/24` | h1b 自己：`10.0.1.12` | `d2:29:2a:88:ce:ee` |
    | `10.0.2.12` | 默认路由 `via 10.0.1.1` | 网关：`10.0.1.1` | `ba:0b:69:c6:63:5d`（br1） |

    因而不能只看 `dev h1a-r1`。还要看目的前缀、是否有 `via`、下一跳及邻居记录。本表是阶段 B，网关 MAC 不应与题 16 阶段 A 的 `r1-h1a` MAC 混用。

21. **第一帧只在 r1 内经过 br1 的二层转发，没有进入替别人转发 IPv4 包的流程。** 它的目的 MAC 是 h1b，网桥把它送往 h1b 的桥端口。第二帧的目的 MAC 命中网关 br1 的本地地址，帧交给 r1 的协议栈；其中 IPv4 目的地址却是远端 h2b，因此需要查路由并走三层转发。namespace 是网络对象的容器，位于同一个 namespace 内的二层与三层逻辑仍有不同职责。→ 2.1、6.1、6.8 节

22. 在题设的接口、路由与邻居解析均正常、无额外过滤条件下：→ 1.5、4.1、6.5、6.8 节

    | 通信 | r1 的 `ip_forward=0` 时 | 原因 |
    | --- | --- | --- |
    | h1a → h1b | 可通 | br1 做二层交换，不需要 IPv4 路由转发 |
    | h1a → `10.0.1.1` | 可通 | 目的地址属于 r1 自己，由本机接收并回应 |
    | h1a → h2b | 不通 | 需要 r1 把目的不属于自己的 IPv4 包转发到上联 |

    所以 ping 通网关只说明这次到网关自身的请求与回复成功，不能证明它会转发到其他网段。

## 七、`ttl=62` 与 traceroute 的“三跳”矛盾吗

23. **`ttl=62` 是 Echo Reply 到达 h1a 时的剩余 TTL。** 在已知 h2a 的回复初始值为 64 的受控实验里，结合已知拓扑，可判断回程经过 r2、r1 两次路由转发，即 $64-62=2$。traceroute 的第三行是最终目的主机 h2a，不是第三台中间路由器，两者没有矛盾。这组数据不保证去回程永远对称，也不能在初始 TTL 未知时机械套用“64 减剩余值”。→ 4.3–4.4、5.3 节

24. **TTL=1 的请求在 r1 停止，TTL=2 的请求在 r2 停止。** 相应的转发过程中 TTL 耗尽，路由器丢弃请求，并可生成 ICMP Time Exceeded，Type 11；本例的“传输途中 TTL 超时”为 Code 0。`10.0.1.1` 和 `10.0.12.2` 是本次返回差错报文使用的源地址，不是设备的全部接口清单；也不应把本次选源结果推广成所有路由器都必须选择同一类接口。→ 4.3 节；RFC 792、RFC 1812 §4.3.2.4

25. **中间 TTL 耗尽通常返回 ICMP Type 11 / Code 0；UDP 探测抵达目标的未监听端口时返回 Type 3 / Code 3（Port Unreachable）。** 普通 UDP traceroute 用这些不同响应区分中途和终点。每行三个时间是从探测源发出各自探测包，到收到对应响应的往返时间（RTT）；包含去程、设备生成响应的处理时间和响应回程。不同跳的探测不是同一个包，响应路径、排队与调度也可能不同，因此相减不能直接得到 r1–r2 的单程链路时延，甚至可能得负数。→ 4.4、5.3 节

26. **加入普通透明网桥不会因桥接本身多出 traceroute 跳数。** 网桥不递减 IP TTL，也不因此产生 TTL 耗尽响应。`* * *` 只表示相应探测未在等待时间内收到可用响应：可能是探测没通过，也可能是 ICMP 被过滤或限速，或响应回不来；路由器仍可能正常转发其他业务。应结合后续跳是否出现、其他探测方式及业务抓包判断。→ 1.5、4.3–4.4、6.5 节

## 八、同样 100% 丢包，断在去程还是回程

27. **第一行是发往 h2a 的请求，第二行是 h2a 发出的回复。** 在本题受控环境中，二者说明请求到达右侧链路，且目标已作答；源端的 `100% packet loss` 仅表示该次 ping 没收到对应 Echo Reply，不能倒推所有请求都未到达。还应在 r2 的 `r2-r1` 接口抓取**向 r1 发出的**回复，结合接口方向、MAC、Echo 标识符与序号比对。只在 `r2-h2a` 看到回复进入 r2，不能证明它已经从另一接口离开。→ 4.2、5.5 节

28. **若 r2 仅关闭转发，来自 h1a 的这个请求应到达 `r2-r1`，但不应被转发到 `r2-h2a`，h2a 因而不会为它生成回复。** 这说的是匹配本次源/目的地址及 Echo 标识的报文，并不是右侧链路绝对没有任何流量。如果结果不同，应核对操作是否发生在 r2、开关当前值、抓包接口与启动时机，以及源校验、过滤规则或其他同时变化的条件。严格反向路径过滤可能把不符合反向路径检查的入包提前丢掉；因此不能在未核实条件时，把所有“没看到包”都归为同一个原因。→ 4.1–4.2、4.5、5.5 节

29. **情况甲断在回复通过 r2 的阶段，情况乙断在请求通过 r2 的阶段。** 以下均按题单的单一故障条件推演；其中甲在右侧链路有请求和回复的现象可与原讲义节选核对，其余预测仍应通过实际观察验证。→ 4.1–4.2、5.5 节

    ```mermaid
    %% review-answer:diagnosis
    flowchart LR
        subgraph A["情况甲：r2 缺回程路由；两台路由器开启转发"]
            A1["h1a"] -->|"请求"| A2((r1)) -->|"请求"| A3((r2)) -->|"请求"| A4["h2a"]
            A4 -.->|"回复到此停止：无回程路由"| A3
        end
        subgraph B["情况乙：r2 关闭转发；路由保持完整"]
            B1["h1a"] -->|"请求"| B2((r1)) -->|"请求到此停止"| B3((r2))
            B3 ---|"链路仍在，但未转发请求"| B4["h2a：未生成对应回复"]
        end
    ```

    *图 1：阶段 A 的两种单一故障，按题设推演。实线箭头标请求路径，虚线箭头标回复路径；乙右侧连线只表示链路存在。两图节点布局相同，地址沿用题单，不涉及带宽或时延测量，也不绘制可能产生的 ICMP 差错报文。*

    | 记录项 | 情况甲：r2 缺回程路由 | 情况乙：r2 关闭 IPv4 转发 |
    | --- | --- | --- |
    | 请求路径 | h1a → r1 → r2 → h2a，完整到达 | h1a → r1 → r2，在 r2 停止 |
    | 回复路径 | h2a → r2，在 r2 停止；无匹配路由去 h1a | h2a 没收到这次请求，不生成对应回复 |
    | `r2-h2a` 可见的对应 Echo 报文 | Request 与 Reply | 两者都不应出现 |
    | 一次附加检查与判据 | 在 r2 查询去 `10.0.1.11` 的路由；题设下无可用路由 | 在 r2 读取 `net.ipv4.ip_forward`；应为 0 |
    | 最小恢复 | 补回 r2 到 `10.0.1.0/24` 经 `10.0.12.1` 的路由 | 恢复 r2 的 IPv4 转发开关为 1 |
    | 恢复后确认 | 两端各发起 ping；关联同一 Echo 的请求与回复，并确认回复从 r2 发往 r1 | 两端各发起 ping；确认请求能从 r2 发往 h2a，回复能返回 |

    **诊断结论示例**：甲中，右侧抓到来自 h2a 的 Echo Reply，说明目标已经处理请求；r2 缺少到回复目的 `10.0.1.11` 的路由，回复不能继续向左转发。乙中，路由表完整仍不足以转发：r2 关闭了 IPv4 转发，请求没有送到 h2a，因此右侧没有这次 Echo 交互。这里不把某条 ICMP 差错必定返回源端作为判断前提。

    检查与恢复命令如下。只对实际注入的故障执行对应恢复项；`route replace` 可在原路由不存在时添加，也可重复恢复到指定值。

    ```bash
    # 1. 情况甲：在 r2 检查回到 h1a 的选路
    sudo ip -n r2 route get 10.0.1.11

    # 2. 情况乙：在 r2 检查转发开关
    sudo ip netns exec r2 sysctl net.ipv4.ip_forward

    # 3. 情况甲的恢复项：补回回程路由
    sudo ip -n r2 route replace 10.0.1.0/24 via 10.0.12.1 dev r2-r1

    # 4. 情况乙的恢复项：重新启用 IPv4 转发
    sudo ip netns exec r2 sysctl -w net.ipv4.ip_forward=1

    # 5. 从两端分别发起往返验证
    sudo ip netns exec h1a ping -c 3 -W 1 10.0.2.11
    sudo ip netns exec h2a ping -c 3 -W 1 10.0.1.11
    ```

    若抓包与预测相反，先检查是否真的只改变了那一项、甲是否另有默认路由、乙的开关是否又被改回；再检查抓包是否覆盖该次发送，地址/接口是否属于阶段 A，是否存在 `rp_filter` 或其他过滤。恢复后的双向 ping 是连通性验证，不能证明所有协议或负载下都没有问题。

## 九、不看输出也要会

30. **三层网关地址应属于 br1，两个主机侧接口只作为桥端口，上联 `r1-r2` 继续独立承担三层互联。** 移除旧地址避免把三层配置留在已交由网桥管理的端口；接口入桥建立二层连接；把地址配到 br1，才使 r1 的协议栈通过网桥接入这个 LAN。完成后 `10.0.1.0/24` 的直连路由应是 `dev br1`。这不是原子迁移，中间步骤可能短暂影响通信。→ 2.1–2.2、6.1–6.4 节

    r1 内的关系如下；br1 与桥端口均在同一个 r1 namespace 内，**不是额外的独立主机**：

    ```mermaid
    %% review-answer:bridge
    flowchart LR
        H1["h1a：10.0.1.11/24"] ---|"veth"| P1
        H2["h1b：10.0.1.12/24"] ---|"veth"| P2
        subgraph R1["r1 的 Network Namespace"]
            P1["r1-h1a：桥端口，无 IP"] --- BR["br1：10.0.1.1/24"]
            P2["r1-h1b：桥端口，无 IP"] --- BR
            BR -.->|"本地投递与三层转发"| IP(("IPv4 查表"))
            IP -.-> UP["r1-r2：10.0.12.1/30，不入桥"]
        end
        UP ---|"veth"| R2(("r2：10.0.12.2/30"))
    ```

    *图 2：阶段 B 的左侧网桥与网关。外部实线表示 veth 链路，r1 内部实线表示桥端口归属；虚线箭头表示跨机架请求在内核中的逻辑处理，不是额外网线。省略右侧 LAN 与回复方向，r1-r2 接口不属于 br1。*

    | 对象 | 二层关系 | 三层配置 |
    | --- | --- | --- |
    | `r1-h1a` | 对端是 h1a 的 `h1a-r1`；`master br1` | 本课基线不配 IP |
    | `r1-h1b` | 对端是 h1b 的 `h1b-r1`；`master br1` | 本课基线不配 IP |
    | `br1` | 管理上述两个桥端口，并提供本机接入点 | `10.0.1.1/24` |
    | `r1-r2` | 对端是 r2 的 `r2-r1`；不加入 br1 | `10.0.12.1/30` |

    同机架帧在两个桥端口间交换；跨机架帧先交给 br1 的本地 MAC，再由 r1 的 IPv4 协议栈查表送往 `r1-r2`。把上联也加入 br1 会改变本讲“LAN 与互联链路分属不同二层域”的设计，不能当作等价操作。

31. **以 h1a → h2a 为去程，四条手工路由和两个转发开关如下。** 表中的方向是相对于这次会话命名，反过来由 h2a 发起时，去回程角色也反过来。→ 4.1–4.2、5.2 节

    | 节点 | 手工路由 | 此次会话中的用途 |
    | --- | --- | --- |
    | h1a | `default via 10.0.1.1` | 去程第一步 |
    | r1 | `10.0.2.0/24 via 10.0.12.2` | 去程跨到右侧 |
    | r2 | `10.0.1.0/24 via 10.0.12.1` | 回程跨到左侧 |
    | h2a | `default via 10.0.2.1` | 回程第一步 |

    r1 与 r2 的 `net.ipv4.ip_forward` 都必须为 1；还要保留各接口地址产生的直连路由。h1a 和 h2a 只需知道本链路与默认网关，不需要各自保存完整中间链路拓扑。这正是逐跳决策的意义。

32. **普通交换机把共享冲突域分开，但在未划分 VLAN 时仍转发该域内的广播；路由器隔开不同二层广播域。** 现代全双工交换链路本身不发生传统共享介质的碰撞，“每端口一个冲突域”是对设备作用的经典表述。阶段 B 有左侧 `10.0.1.0/24`、互联 `10.0.12.0/30`、右侧 `10.0.2.0/24` 三个二层广播域；中间是仅有 r1、r2 两端的以太网链路。ARP 没有 IP TTL；即便帧里承载 IP，普通网桥也不递减它，所以 TTL 不能替二层环路兜底。STP 把选定的冗余端口置于不转发普通数据帧的状态，使二层有效转发拓扑无环，不是物理拔线。→ 1.4–1.6、5.1、6.1 节

33. **原来有 $N(N-1)$ 条，新增一个网段及其路由器后增加 $2N$ 条。** 原有每台新增一条去新网段的路由，共 $N$ 条；新路由器各配一条去原有网段的路由，又是 $N$ 条。也可计算差值：$(N+1)N-N(N-1)=2N$。这个计数只计算题设中的远端主机网段路由，不含直连项；依赖不能聚合、不用默认路由且每个远端网段各配一条等条件。动态路由自动交换可达性信息、计算并安装下一跳，在链路变化时更新；它不会凭空创造备用链路，也不负责自动完成所有地址规划。→ 3.4 节、模块七思考题 6；衔接第三讲 1.1、1.3–1.4 节

## 十一、“想一想”参考思路

### 启发 1：不同的表回答不同的问题

`FAILED` 表示这次邻居解析或探测没有成功，不直接说明目的网段路由写错。先核对选出的下一跳和出接口是否正确；若正确，应看该链路的地址、接口状态和 ARP 请求/回复，阶段 B 还要查桥端口与 FDB。例如 r1 经 `r1-r2` 去 `10.0.12.2`，应在这条链路找邻居证据，而不是直接去右侧 LAN 查 h2a 的 MAC。邻居失败还可能是对端未回应或过滤，不能只凭 `FAILED` 就认定网线断了。→ 3.1、4.2 节

### 启发 2：局部决定不等于端到端成功

“进程在运行”只确认进程存在；“端口能连接”通常验证到监听端口的传输层建立过程；“业务请求完整返回”还涉及请求解析、业务执行及响应返回，具体覆盖范围取决于请求是否触发数据库等依赖。健康检查应说明自己探测到哪一步、从哪里探测，不能让最浅的一层代替全部业务健康。→ 3.3、4.2 节的证据边界，应用层延伸

### 启发 3：请求与回复是两条独立的证据链

第一次加积分可能已经执行，只是响应丢失；直接重试可能加两次。应用可以为每次业务操作分配请求 ID 或幂等键，让服务端把“已执行的 ID 与结果”同实际业务变更可靠地关联起来，重复请求返回原结果而不再次变更。只在内存里随手记一下并不能自动保证崩溃恢复后的去重，具体保证要看状态保存与事务设计。→ 4.2、5.5 节，应用层延伸

### 启发 4：自动学习既要更新，也要遗忘

迁移后一直沉默，交换机没有来自新端口的源帧证据，旧动态映射可能继续保留，直到老化或其他更新事件发生。迁移后立即发一个源 MAC 不变的帧，新端口上的源地址学习可触发更新。因此长老化时间不是“迁移必定等很久”的充分条件；还要看是否有新流量、学习是否开启、表项是否为可更新的动态项。→ 1.3 节、模块七思考题 2；题 34l

### 启发 5：反例与对照比反复重试更有用

在给定的甲乙两种候选原因之间，`r2-h2a` 是有区分力的观察点：甲有对应请求与回复，乙没有。若只能在 h1a 操作，可结合不同 TTL 的探测、网关可达性和收到的 ICMP 类型缩小范围；但远端不回差错、回程丢失或过滤都可能造成相似结果，不能保证仅凭源端探测唯一定位。报告应保留候选原因和需要进一步取得的证据。→ 4.2–4.5、5.5 节

### 启发 6：让计算看见路径，而不只看见地址

ping 通仅说明这次小报文往返成功，不足以选择大数据交换任务的放置位置。还需要明确数据量与通信模式，测量实际吞吐、RTT 或单程时延、丢包与排队变化，并检查并发流是否共享同一瓶颈；还要结合节点计算能力和负载。最后用应用的完成时间比较方案，不能只凭一次 ping 延迟小就断言作业更快。→ 本讲 6.5、6.8 节；后续第五讲与性能测量内容
