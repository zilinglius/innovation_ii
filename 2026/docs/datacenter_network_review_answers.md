## 一、从“能互通”到“够用”

1. **（1）$8\times7=56$ 组有方向的通信关系。** 一对主机之间可以用一条或多条连接，也可以分时发送、复用已有连接；矩阵的一个格子只汇总这一对主机在本阶段的需求，不记录连接数。**（2）** 外部请求进入前端、把结果返回外部客户端是南北向；worker 之间交换中间结果、参数服务器向 worker 下发模型发生在数据中心内部，是东西向。**（3）** 两两 `ping` 只说明每对主机的少量探测包有往返，样本是“各自单独”发送的。缺少的证据可以是：多对主机同时传输时的接收字节与共同完成时间；共享链路（如源 leaf 上联、目的主机接入口）上的累计负载；一条上联故障后的剩余容量。→ 1.1、1.3 节

2. 结果如下。→ 1.2 节

    | 发送端 ↓ ／接收端 → | `h1a` | `h1b` | `h2a` | `h3a` | 行和 |
    | --- | ---: | ---: | ---: | ---: | ---: |
    | `h1a` | 0 | 0 | 50 | 50 | 100 |
    | `h1b` | 30 | 0 | 50 | 0 | 80 |
    | `h2a` | 0 | 0 | 0 | 0 | 0 |
    | `h3a` | 0 | 0 | 40 | 0 | 40 |
    | 列和 | 30 | 0 | 140 | 50 | 220 |

    - **（1）** 行和合计与列和合计都是 220 MB。最突出的是**多对一**：`h2a` 一列有三个非零项，共 140 MB，应先检查 `r2 → h2a` 的接入链路（r2 的 `r2-h2a` 发送方向）以及到达它的共享路径；`h1a` 一行有两项，也带一点一对多的形态。
    - **（2）** 机架 1 向外发送 $50+50+50=150$ MB（`h1a → h2a`、`h1a → h3a`、`h1b → h2a`）。`h1b → h1a` 在 br1 内交换，不上上联；`h3a → h2a` 从机架 3 经 spine 到机架 2，也不经过机架 1。
    - **（3）** `r2 → h2a` 承载 140 MB：$8\times140/100=11.2$ 秒。机架 1 的 150 MB 若全部碰撞在一条 100 Mbit/s 上联：$8\times150/100=12$ 秒，超过 11.2 秒，瓶颈从目的接入口换到这条上联。三条 50 MB 的流在两条上联上最好也只能分成 100 : 50，较忙的一条需 8 秒，仍低于 11.2 秒。
    - **（4）** 不能。0 只表示本阶段没有这项需求；是否连通要用 `ping` 等可达性证据另行判断。

3. **（1）甲的 64 Mbit/s 是按计划推出的“所需平均速率”，不是测量值；乙的 64 Mbit/s 是测量窗口内的平均速率：$8\times80/10=64$ Mbit/s。** 只知道计划传 80 MB，不能断言网络达到了这个速率。**（2）** 前 4 秒：$8\times48/4=96$ Mbit/s；后 6 秒：$8\times32/6\approx42.7$ Mbit/s。10 秒平均值掩盖了时间分布：前 4 秒已接近 100 Mbit/s 的接入容量，短时排队与竞争可能就发生在这一段。**（3）** 统一节点顺序与方向（行＝发送端）、窗口长度与起止时刻、计数口径（接收端应用有效字节，还是包含首部与重传的接口字节）、单位（十进制 MB、bit/s）。→ 1.2 节

## 二、leaf-spine：路有几条，经过谁

4. **（1）** STP 靠阻断部分链路消除环路，冗余链路平时闲置，广播域还覆盖所有机架。机架间改用三层路由后，冗余链路成为等价路径，可以用 ECMP 同时承载流量；ARP 广播留在机架内，链路故障由路由协议处理。**（2）** $2\times4=8$ 条；每个 spine 至少 4 个下联端口，每个 leaf 至少 2 个上联端口，另加服务器端口。**（3）** 加第 5 个 leaf：两个 spine 各需 1 个空闲端口，新 leaf 需 2 个上联端口。加第 3 个 spine：4 个 leaf 各需 1 个空闲端口，新 spine 需 4 个下联端口。加 spine 后跨机架最短路径变为 3 条。两种扩展都还要核对端口速率、布线与控制平面规模。→ 2.1–2.4 节

5. 地址按 $k=2(\text{leaf}-1)+(\text{spine}-5)$ 推出。→ 2.2–2.5 节

    - **（1）** 经 r5：h2a → r2（`10.1.2.0/30`）→ r5（`10.1.6.0/30`）→ r4 → h4b；经 r6：h2a → r2（`10.1.3.0/30`）→ r6（`10.1.7.0/30`）→ r4 → h4b。两条都经过 r2、一台 spine、r4，共三台转发设备。
    - **（2）** 第 1 行是网关 10.0.2.1（r2 的 br2）。第 2 行 10.1.3.2 是 $k=3$ 链路的 spine 端，即 r6 的 `r6-r2`，这次探测经过 r6。第 3 行的 10.1.7.1 是 r4 的 `r4-r6`，10.1.6.1 是 r4 的 `r4-r5`，两者都表示 r4。第 4 行是目的主机 10.0.4.12，共 4 行；网桥不是 IP 跳。注意第 3 行只能用来认设备：Linux 默认（`icmp_errors_use_inbound_ifaddr=0`，本次补测在实验床的 r3 上读到 0）用“发出 ICMP 差错的那个接口”的主地址作源地址，而 r4 回到 10.0.2.0/24 有两个等价下一跳，显示哪一个地址取决于回程的选择，不一定是探测进入的那条链路。
    - **（3）** r2–r5 断开后经 r6 的路径仍在；r2 的上联总容量减半，100 档时从 200 降到 100 Mbit/s，收敛比从 1:1 变为 2:1。

6. **（1）第一行没有 `via`：10.0.1.12 与 h1a 同网段，h1a 直接 ARP 解析 h1b，帧的目的 MAC 是 h1b `eth0` 的地址；第二行 `via 10.0.1.1`：先交给网关，目的 MAC 是 br1 的地址，IP 目的地址仍是 10.0.3.11。** **（2）** 交换与路由的分界在 r1：`-i any` 一次覆盖 r1 的网桥端口与两条上联，`-Q out` 只看 r1 把包从哪个接口发出去，避免同一包的入、出各记一次。`icmp[0] = 8` 只留下 echo request，排除回复；`src host 10.0.1.11` 排除其他主机与控制报文。在 h1a 的 `eth0` 上加 `-e` 打印链路层首部，也能凭目的 MAC 区分“直接交给 h1b”与“交给网关”，但看不到 r1 选了哪条上联。**（3）** 这一行只证明“这一个 ICMP 请求从 `r1-r6` 发出”。其他探测与连接的哈希输入不同，可能选 r5；回复走哪条路由 r3 决定；它也没有覆盖 r6 之后的部分。可以写“本次探测经 r6”，不能写“h1a 到 h3a 走 r6”。→ 2.5 节

## 三、ECMP：三个环节分别核对

7. **（a）由 `lsrd` 的 SPF 完成（Lab 2 R7，需 `--ecmp` 保留并列首跳），看守护进程的 RIB；（b）由 `lsrd` 按 R8 调用 `ip route replace` 写入，看 `ip route show 10.0.3.0/24` 是否有多行 `nexthop`；（c）由 Linux 内核在转发每个包时按哈希选择，看各出接口上的真实报文（SYN 与数据包出口）或 `tc -s` 计数。** 相邻两件不成立的例子：→ 3.1 节

    | 前一件成立 | 后一件不成立的情形 |
    | --- | --- |
    | 有两条物理路径 → SPF 算出两条 | 两条路 cost 不同；基础版只保留 rid 最小的首跳；某条链路的邻接没有双向 Full，按 R7 不算边 |
    | SPF 算出两条 → 内核装了两条 | 安装时没有写成 multipath；安装失败；内核里的路由被删掉而守护进程不知道（题 31 乙，修复前：r6 的 RIB 有、内核 `MISSING`） |
    | 内核装了两条 → 业务用了两条 | 只有一条连接；同一主机对且哈希策略为 0（题 10）；多条连接哈希碰撞 |

8. **（1）策略 0 只用源、目的 IP 计算转发哈希，同一对主机的 8 条连接得到相同哈希，全部走同一个下一跳；策略 1 把协议与端口也纳入，不同连接有机会分开，但不保证 4 : 4。** **（2）** 内核文档写的默认值是 0，课堂脚本把路由器设成了 1；同一现象在两种取值下的解释完全不同，所以要先读实际值。本次补测在新建的 network namespace 中读到 0。**（3）** 不矛盾。“同一组哈希输入”不只包括报文头里看得见的字段：在本实验床中，转发的 TCP 报文带着发送端 socket 计算的四层哈希（每条连接随机产生），策略 1 会直接复用它。新连接即使五元组相同，哈希也可能不同；同一条连接内部则保持稳定，只有在超时重传等情况下可能重新选择（Lab 3 任务 5 的说明）。→ 3.2 节；Lab 3 任务 5

9. **（1）约 50 Mbit/s，应用有效速率略低。** 按流 ECMP 让一条连接只选一个下一跳，另一条上联对它没有用。**（2）约 $\min(2\times50,\ 100)=100$ Mbit/s，受两条上联合计容量与发送主机接入口的约束。** 47.59 Mbit/s 对应一条 50 Mbit/s 上联；93.52 Mbit/s 同时接近两条上联之和与 100 Mbit/s 的接入口，这一组数据分不出是哪一项在起作用。**（3）** 需要按包或按 flowlet 在路径间分配，或使用多路径传输协议。主要代价是乱序与接收端的重排缓冲，以及实现复杂度；原讲义不展开。→ 3.3、3.5 节

10. **（1）策略 0 下转发哈希只看源、目的 IP，8 条连接属于同一对主机，必然选同一个下一跳（这次是 r6）。** 它们共享一条 50 Mbit/s 上联，所以吞吐 46.95 Mbit/s 与单流的 47.59 Mbit/s 几乎相同；略低的部分没有在一次运行中进一步区分。**（2）每条上联的 50 Mbit/s 由经过它的连接分享。** iperf3 运行约 5 秒：r5 上那 1 条连接独占一条上联，约 $8\times28.70/5\approx46$ Mbit/s；r6 上 7 条连接合计 29.36 MB，平均每条约 4.19 MB，约 6.7 Mbit/s。后者是按路径汇总后的平均值，补测没有记录 7 条连接各自的速率。**（3）** 流数、字节、吞吐回答的是不同问题：1 : 7 的流数比，对应的却是接近 1 : 1 的字节比。改为每条连接固定 3.75 MB 时（纸面估算）：r5 上的连接约 $8\times3.75/46\approx0.65$ 秒完成；r6 上 7 条共 26.25 MB，约 $8\times26.25/47\approx4.5$ 秒才全部完成，最后完成的都在 r6 上。若恰好 4 : 4，每条路径 15 MB，约 2.5 秒。作业等最慢的连接，挤的一侧决定完成时间。→ 3.4、3.5 节

## 四、收敛比与完成时间下界

11. **（1）收敛比（过订阅比）是容量之比；路由收敛说的是拓扑变化后多久重新算好、装好路由，两者只是中文名相近。** **（2）** 下联 $2\times100=200$，上联 $2\times50=100$，收敛比 2:1。只把下联按全双工翻倍、上联不翻倍，会得到 4:1，两侧口径不一致；两侧都按同一方向计算才对。“上联 : 下联 = 1:2”是倒过来写的同一个比值，换算后一致。**（3）** 200 : 100，即故障后 2:1。→ 4.1 节

12. **（1）两条流碰撞的概率为 $2\times(1/2)^2=1/2$；三条流全挤在同一路径为 $2\times(1/2)^3=1/4$；三条流中至少两条同路的概率为 1。** 三条流只有两条路径可选，必有两条同路。**（2）** 按流数，路径 2 更忙（4 条对 1 条）；按字节，路径 1 更忙（约 1 GB 对 4 MB）。**（3）** 不能。普通哈希 ECMP 只按报文字段和哈希配置选路，不读取队列长度；flowlet、自适应负载均衡不在本讲范围。→ 3.4 节

13. 下界逐类计算如下。→ 4.3 节；7.2 节思考题 2

    - **（1）** 分路：每条上联 100 MB，$8\times100/50=16$ 秒；碰撞：一条上联 200 MB，32 秒。
    - **（2）** 100 档：发送端接入各 30 MB，2.4 秒；源 leaf 上联每台合计 60 MB，均衡时每条 30 MB，2.4 秒，碰撞时 60 MB，4.8 秒；spine → r3 共 120 MB，均衡时每条 60 MB，4.8 秒，最坏全压在一条上为 9.6 秒；r3 → h3a 承载全部 120 MB，9.6 秒。**下界 9.6 秒，由接收端接入口决定**，无论哈希怎样分布都不会更低。
    - **（3）** 50 档、两个 spine 各两条流：spine → r3 每条 60 MB，$8\times60/50=9.6$ 秒，与 r3 → h3a 并列；源 leaf 上联每条 30 或 60 MB，即 4.8 或 9.6 秒。下界仍是 9.6 秒，但此时有不止一条链路同时“卡在” 9.6 秒。若三条流挤到同一个 spine，那条 spine → r3 链路承载 90 MB，需 14.4 秒，瓶颈转到 fabric。
    - **（4）** 它不是 TCP 完成时间的预测。它忽略了首部开销（按帧长折算为 $9.6\times1514/1448\approx10.04$ 秒）、建连、慢启动、排队与丢包；多对一传输还可能因浅缓冲丢包、超时而远慢于下界，这是第 07 讲 incast 的内容。

14. **（1）`rate` 是该类的保证速率，`ceil` 是可借用到的上限；本实验两者相同，把这个出口的持续发送速率限制在档位上。它们是配置，不是测得的吞吐。** `class htb 1:10 … leaf 10:` 是 tc 的层级术语：类 1:10 下挂着句柄为 10: 的叶子队列（这里是 fq），与拓扑中的 leaf 交换机无关。**（2）不能。** `tc class show` 只显示指定接口的发送方向；r5 → r3 要看 r5 的 `r5-r3`。课堂脚本对所有 leaf–spine 链路两端都设置了限速，但核对时仍应在相应设备上看。B 条件的共享瓶颈是数据进入 h3a 之前的出口，即 r3 的 `r3-h3a`；h3a 的 `eth0` 发送方向是 h3a 往外发 ACK 的方向。**（3）不能。** veth 报告的 10000Mb/s 只是驱动给出的名义值，没有实际约束意义；不加 `tc` 时 veth 的吞吐取决于 CPU。本次补测在新建的 veth 上读到的正是 `Speed: 10000Mb/s`。→ 4.1、4.5、6.1 节

## 五、overlay：租户看到的网络

15. **（1）underlay 负责 VTEP 之间的 IP 可达，仍是 leaf-spine 与路由；overlay 在其上为各租户提供独立的地址空间与连接关系。** 两个租户的 192.168.10.0/24 放进同一张普通路由表，查到的下一跳会有歧义，必须先按租户分开（VNI 与各自的网桥，或按租户的路由表）。**（2）** 24 位，$2^{24}=16\,777\,216$ 个；802.1Q 的 VLAN ID 为 12 位，4096 个取值，去掉保留值后 4094 个可用。**（3）** 4789。Linux 在 IANA 分配端口之前就实现了 VXLAN，不写 `dstport` 时会使用历史上的非标准端口：本次补测中 iproute2 对此给出警告，建出的设备为 `dstport 8472`。两端端口必须一致，显式写 4789 可以避免依赖默认值。**（4）** 都不能。VNI 是分段标识，不加密，也不预留带宽；CNI 是容器运行时调用网络插件的接口规范，不是隧道协议，也不规定必须用 VXLAN。→ 5.1、5.2、5.6 节

## 六、封装之后：选路与 MTU

19. **（1）若只按外层 IP 哈希，这对 VTEP 之间的所有内层流得到相同哈希，全部挤在一条路径上。VXLAN 让外层 UDP 源端口随内层流变化（RFC 7348 第 5 节），前提是做 ECMP 选择的设备在哈希中使用四层端口，或能解析内层报文。** **（2）** 是 r1 自己：VTEP 就在 leaf 上，r1 选择从哪条上联发出外层报文。r5、r6 去往 10.0.3.0/24 都只有直连 r3 一个下一跳，不再选择。**（3）** 缓存命中时，VTEP 直接沿用缓存里的出口，不再用本包的外层源端口查 multipath 路由，所以外层端口不同的连接可能都走同一条上联；缓存按 CPU 保存，不同 CPU 可能缓存了不同出口，同一连接的包从不同 CPU 发出时就会分到两条上联。外层端口不同不足以证明走了两个 spine：还要看路由的下一跳集合、哈希策略、缓存状态，以及两个出接口上的实际数据包。→ 5.4 节；Lab 3 任务 7

20. **（1）外层 IPv4 20 B ＋ UDP 8 B ＋ VXLAN 8 B ＋ 内层 Ethernet 14 B ＝ 50 B。** IP MTU 限制的是外层 IP 包的长度；外层 Ethernet 首部不属于这个 IP 包，计入的是帧长，不计入 IP MTU。**（2）** 内层带 VLAN 标签时多 4 B：$1500-54=1446$；外层改为 IPv6：$1500-(40+8+8+14)=1430$；两者同时出现：$1500-74=1426$。**（3）** $9000-50=8950$。→ 5.5 节

21. **（1）1450 是 IP 包总长：1422 B 数据 ＋ 8 B ICMP 首部 ＋ 20 B IPv4 首部；1430 是回复中 ICMP 报文的长度（8 ＋ 1422），不含 IPv4 首部。** **（2）** `local error: message too long, mtu=1450` 与 `+1 errors` 说明包在源端就被拒绝，根本没有发出。若真正过不去的是中途 MTU 更小的路由器，它会丢弃设置了 DF 的包并回送 ICMP“需要分片”（类型 3、代码 4），`ping` 显示类似 `From <路由器地址> … Frag needed and DF set (mtu = …)`；如果这类 ICMP 被过滤，就只剩无声的丢包，即路径 MTU 黑洞。**（3）** 只摘 `100% packet loss` 丢掉了定位信息，把源端拒绝错写成远端丢包。在 `set -e` 脚本里，预期失败的命令要显式处理，例如 `classroom.sh mtu` 的写法：放在 `if` 里，成功反而报错退出。→ 5.8 节

## 十一、从程序员视角再想一步

### 1. 需求、资源与映射分开建模

参考思路：负载均衡器里，请求分布是需求，后端实例是资源，调度算法是映射；数据库分片里，访问模式是需求，节点是资源，分片键是映射。只扩资源而不看映射，容易出现“加了机器却不变快”：新增的容量没有落到热点上。题 25 中给 C 增加 spine 就是这样。

### 2. 哈希分散的是“个数”，不是“负载”

参考思路：哈希保证的是“键的个数”大致均匀，不保证每个键的负载相同。热点键、大对象与大象流都是“一个单位就占满一个分片”。常见做法有拆分大对象、给热点键加副本或随机后缀、按负载而不是按个数迁移分片；网络里对应的是把大流拆成多条连接、flowlet 或自适应负载均衡。

### 3. 先算下界，再看测量

参考思路：测量值远高于下界，就去找下界没有计入的东西：碰撞、开销、排队、CPU。测量值低于下界，几乎一定是测量错了：少传了数据、没有等接收确认、单位混用（题 26）。写程序前先估一个数量级，例如“这次 I/O 至少要读多少字节、磁盘每秒能读多少”，能让很多性能问题在动手前就暴露。

### 4. 名字空间隔离不等于资源隔离

参考思路：容器的 namespace、虚拟机、多租户数据库的 schema，都让租户“看不见彼此”，但 CPU、磁盘、网络仍可能共享，于是出现吵闹邻居。要保证资源，需要在共享点分类（按租户打标）、预留（配额、最小速率）并调度（优先级、公平队列）；只限制邻居的上限，不等于保证了自己的下限。

### 5. 部分失败比全部失败更难发现

参考思路：一个固定的 `ping` 或健康检查只走一条路径、一个分片，恰好避开故障时会一直报告“正常”。探测要覆盖不同的路径与分片，例如用多个源端口、多对主机，并按路径分组记录成功率；只看全局的平均成功率，一半失败也可能被平均掉。

### 6. 期望状态要和实际状态对账

参考思路：只和自己的记录比，发现不了别人改动、或系统自己清掉的状态；Lab 2 的 `router.py` 正是因为题 31 乙才加上了每 2 秒一次的对账。可靠的控制器会定期从实际系统读回状态再比较（Kubernetes 控制器的周期性重新同步就是一例），并在关键事件（链路变化、进程重启）后立即对账。代价是读取开销与可能的抖动，所以通常结合事件触发与较长周期的全量对账，并为每条状态标明归属，例如 `proto 200`。

本回顾已完成矩阵、配置、抓包与计时的复盘；[Lab 3](../experiments/03/README.md) 要求你搭建自己的实验床、测量并解释，学生实现须独立验收，样例中的端口、路径比例与用时不是验收常数。[第 06 讲](network_measurement.md)在同一实验床上把吞吐、延迟、抖动与丢包变成可比较的网络画像。

- [Lab 3 指导书](../experiments/03/README.md)：地址约定、帧级下界（任务 3）、哈希与 socket 哈希复用（任务 5）、租户共享（任务 6）、VTEP 路由缓存（任务 7）；[`classroom.sh`](../experiments/03/classroom.sh) 是课堂观察与本次补测的实验床入口。
- [RFC 7348](https://www.rfc-editor.org/rfc/rfc7348)：第 5 节的首部格式、UDP 端口与源端口建议。[RFC 7938](https://www.rfc-editor.org/rfc/rfc7938)：第 5.2.1、5.2.2、6.1 节的 ASN 规划与路径限制。
- [Linux IP Sysctl](https://docs.kernel.org/networking/ip-sysctl.html)：`fib_multipath_hash_policy`（默认 0）、`ignore_routes_with_linkdown`（默认 0）、`icmp_errors_use_inbound_ifaddr`（默认 0）与 `rp_filter` 的宽松模式。[Linux VXLAN 文档](https://docs.kernel.org/networking/vxlan.html)：设备参数与目的端口。
- [Linux SNMP counter](https://docs.kernel.org/networking/snmp_counter.html#ipinaddrerrors-ipextinnoroutes-and-ipoutnoroutes)：`IpExtInNoRoutes` 的含义。`TcpExtIPReversePathFilter` 未在该文档中说明，本文按计数器名称解释，并用它与请求数的吻合作为旁证。
- `man 8 ip-route`、`man 8 ip-monitor`、`man 8 tc-htb`、`man 8 tcpdump`、`man 8 nstat`：查表、路由事件、限速、抓包与内核计数器的观察工具。复现时另记实际内核、发行版与 `sysctl` 读数。
