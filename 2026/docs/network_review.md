34. ● 判断下列说法是否正确；错的请改正，并指出讲义里对应的小节。

## 九、从程序员的角度：第 01 讲给我们的启发

第 01 讲讲的是协议，但其中许多设计决定，和我们平时写程序时面对的是同一类问题。下面每一条先说讲义里的事实，再说它对写程序的人意味着什么，最后留一个问题。

### 启发 1：分层就是接口契约

讲义 1.1 节说，每一层只定义两件事：与对等层之间的通信规范（协议），以及向上层提供的服务接口。换掉下层（有线换 Wi-Fi、铜缆换光纤），`send()` 这一行代码不用改。这与软件里的模块划分同构：模块之间靠接口相连，实现可以替换；一层的首部，就是这一层的“函数参数”——只放足以完成本层工作的信息，不解释载荷。

> **想一想**：你写过或用过的系统里，哪一层相当于 IP 首部——只携带足以转发、分派的元信息，对载荷的内容一无所知？它的“载荷”是什么？

### 启发 2：封装是“不透明字节 + 一个类型标签”

“Hello TCP!” 往下走时，每一层把上一层交来的整个数据单元当作不透明的载荷，在前面加一个首部；往上走时，接收方仅凭首部里的一个字段决定交给谁：EtherType `0x0800` → IP，Protocol `6` → TCP，目的端口 `9000` → 监听的套接字。这正是所有“信封套信封”式序列化格式的原型：TLV、Protobuf 的 wire type、HTTP 的 `Content-Type`。写协议解析器的两条规矩由此而来：只解析自己这一层的首部；靠首部里的长度和类型字段前进，不猜。

> **想一想**：选做观察 A 里，tcpdump 在第二、三个分片上“解析不下去了”，显示成 `ip-proto-1`，因为它需要的标签在另一个包里。你的程序做流式解析时，遇到“首部在上一个数据块里”的情况会怎样？

### 启发 3：端到端原则——可靠性放在两端，中间只管尽力而为

IP 无连接、尽最大努力交付；分片丢一片就整个重传；ICMP 只报告、不修复。可靠性是 TCP 在两端用序号、累积确认和超时重传做出来的。校验和的分工也体现这一点：FCS 逐跳校验整帧，IP 校验和只校首部（每跳重算，代价要小），TCP 校验和含伪首部、端到端覆盖全部数据。分布式系统同理：网络会丢、会重、会乱序，中间的组件不能替你保证语义；重试、幂等、去重的责任在应用的两端。“RPC 超时了”不等于“对方没执行”。

> **想一想**：你调用一个远程接口超时后重试，服务端可能收到两次同样的请求。TCP 用什么机制保证应用层不会“收到两次”同一段数据？你的应用层协议里有对应的东西吗？

### 启发 4：字节流没有消息边界

4.2 节的表格里有一格叫“面向字节流：应用层无边界，需自行分包”。选做观察 B 中 `nc` 一次就收到完整的 “Hello TCP!”，只是因为 10 个字节既小于 MSS、又没有被内核合并或拆开——这是巧合，不是保证。“一次 `recv()` 就是一条消息”是网络编程里最常见的 bug。应用层必须自己定帧：长度前缀、分隔符或固定长度；HTTP 的 `Content-Length` 与 chunked 编码解决的就是这个问题。

> **想一想**：把 “Hello TCP!” 换成一个 1 MB 的文件通过 `nc` 发送，接收端的 `recv()` 会被调用几次？这个数字能预测吗？TCP 到底保证了什么、没保证什么？

### 启发 5：缓存不是“对 / 错”两态

2.4 节的邻居表有 `REACHABLE`、`STALE`、`DELAY`、`PROBE` 四种状态；步骤四的第 5、6 帧就是 ns2 在“复查”一条从广播里顺便学来、从未确认过的表项——过期的条目照用，用了之后再去验证，验证失败才作废。这是 stale-while-revalidate 的内核版本。DNS 的 TTL、HTTP 缓存、服务发现的本地缓存，用的都是同一个模式：缓存条目带着“信心程度”，而不是简单的有或没有。

> **想一想**：如果 ARP 表只有“有 / 没有”两态，会付出什么代价——每隔 30 秒对每个邻居广播一次，还是一个错误的 MAC 一直用到天荒地老？

### 启发 6：三次握手、TIME_WAIT 与迟到的旧消息

4.4 节解释“为什么不是两次”：一个在网络里滞留许久的旧 SYN 会让服务端白白建立连接；“为什么要 TIME_WAIT”：让旧连接的报文在网络中自然消失，以免混进同一五元组的新连接。两者防的是同一件事——迟到的旧消息冒充新消息。任何有状态的协议都得处理它：序号、纪元（epoch）、连接 ID。程序员会亲身撞上的版本是服务重启时的 `bind: Address already in use`——那正是 `TIME_WAIT` 在保护上一条连接；`SO_REUSEADDR` 是在告诉内核你了解这个风险。

> **想一想**：你设计一个自定义的请求—应答协议，某个响应迟到了一个超时周期才到达，客户端怎么知道它属于哪一次请求，而不是把它当成下一次请求的响应？

### 启发 7：两种背压

TCP 首部的 Window 字段是接收方在说“我的缓冲区还剩这么多”，这是流量控制，保护接收方；发送方还要受拥塞窗口约束，那是拥塞控制，保护网络（第 07 讲）。生产者—消费者、消息队列、异步 I/O 里也有这两种压力：下游处理不过来，和共享通道被挤爆。没有背压（backpressure）的系统在负载上来时，先是延迟暴涨，然后内存耗尽。

> **想一想**：如果 `send()` 永远不阻塞、也从不返回 `EAGAIN`，你写出去的数据去了哪里？谁来告诉生产者“慢一点”？

### 启发 8：大消息谁来切

3.3 节的分片是反面教材：任一分片丢失就全部重传，后续分片不带传输层首部，中间设备无法处理。工程对策是“干脆不分片”——DF = 1 加 Path MTU Discovery，TCP 用 MSS 自己把数据切成合适的段。原则是：把大对象切块的责任交给知道边界与重传单位的那一层，而不是下面某个不知道内容的层。gRPC 的最大消息尺寸、对象存储的分块上传，都是这个原则。

> **想一想**：一个要分成 40 片的 IP 数据报，在丢包率 1% 的路径上完整到达的概率是多少？如果改成 40 个各自独立确认与重传的 TCP 报文段，情况会有什么不同？

### 启发 9：一台机器里的一个机房

6.1 节列出 namespace 各自拥有的东西：接口、地址、路由表、邻居表、端口空间、防火墙、内核参数。这不是虚拟机，而是内核把同一套网络对象实例化了多份。容器网络建立在这之上（思考题 4：`-p 8080:80` = namespace + NAT）。对写程序的人来说，它是一个免费的实验室：在一台机器上模拟多台主机、网络分区、延迟与丢包（后续实验会用 `tc`），不需要真的准备一堆机器。理解了它，排查容器网络问题时才知道该到哪个 namespace 里看。

> **想一想**：在容器里执行 `curl localhost:8080` 访问不到宿主机上监听 8080 的服务。第 01 讲的哪一条能解释这件事？

### 启发 10：预测、测量、解释

讲义里理论与实测对不上的地方不止一处：帧长算出 64 字节，抓到 76 字节；ARP 帧“至少 64 字节”，抓到 42 字节；四次挥手，抓到三个报文。每一处差异背后都是一个实现细节——默认开启的时间戳选项、抓包点在网卡之上、被动关闭方合并了 ACK 与 FIN。真实系统总带着“默认开启的选项”，只读规范不看线上的字节，预测就会差 12 字节。所以调网络程序的第一件事，是在协议边界抓包看事实，而不是加日志猜；tcpdump 就是网络程序员的 `print`。

> **想一想**：本讲的动手实验里，有哪一处“预测与实测不一致”是你之前不知道的？把它和它的解释记下来——这就是本课程“预测、测量、解释”三步法的第一次练习。

这十条有一个共同点：网络对程序不是黑盒。从 `send()` 到线上的字节，每一步都有规则，也都能观测。本课程后面要做的“让计算看见网络”，就从这里开始。
