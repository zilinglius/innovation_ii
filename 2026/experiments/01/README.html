              第一节目标

              实验目标

              1. 补全第 02 讲模块 6.4 留白的右侧机架，确认自己真的掌握了 Linux 网桥的三条规矩。
              2. 跑通并读懂本目录提供的拓扑脚本，能说清它靠什么做到"重复执行不报错"，以及这个做法的代价。
              3. 把实验床从两个机架扩展到三个，量化静态路由随规模的增长——这是下一个实验存在的理由。
              4. 用 tc netem 给链路加延迟，先预测 RTT 再实测，解释差距。
              5. 在被随机破坏的实验床上，按定位清单找出故障，并写清你的判据（不是猜对，是能证明）。
              第二节准备

              预备知识与工具

              先读：

              • 第 01 讲　计算机网络基础与 Linux 网络虚拟化
              • 第 02 讲　二层交换与静态路由，尤其是 2.2 节（网桥三条规矩）、3.1 节（转发决策流程）、4.2 节（"ping 不通"的定位顺序）

              bash
              # 1. iproute2（提供 ip / bridge / tc）、ping、tcpdump 通常已自带；traceroute 多数发行版需要手工安装which ip bridge tc ping tcpdump traceroutesudo apt install -y iproute2 iputils-ping tcpdump traceroute
              bash
              # 2. 确认内核带 netem（进阶任务需要）。四条命令都不报错即可sudo ip link add nettest0 type veth peer name nettest1sudo tc qdisc add dev nettest0 root netem delay 1mssudo tc qdisc del dev nettest0 rootsudo ip link del nettest0

              如果第 2 步报 Error: Specified qdisc kind is unknown.，说明当前内核没有 sch_netem 模块。装上 linux-modules-extra-$(uname -r) 后重试；某些精简内核（容器、部分云镜像）不提供该模块，需要换用标准发行版内核。

              任务 4进阶

              给链路加延迟：先预测，再实测

              tc netem 可以在任意接口上人为制造延迟、抖动和丢包。本任务只用延迟。

              bash
              # 10. 先量基线：跨机架的 RTTsudo ip netns exec h1a ping -c 10 -q 10.0.2.11

              本机实测的基线约为 0.07 ms（namespace 之间是内存拷贝，几乎没有传播时延）。

              先写下你的预测，再往下做：

              • 在 r1 的上行口 r1-r2 上单向加 20 ms 延迟，h1a → h2a 的 RTT 会变成多少？
              • 如果在 r2 的 r2-r1 上也加 20 ms，RTT 又是多少？
              • 同机架的 h1a → h1b 会受影响吗？
              bash
              # 11. 在 r1 的上行口加 20ms 单向延迟sudo ip netns exec r1 tc qdisc add dev r1-r2 root netem delay 20mssudo ip netns exec h1a ping -c 10 -q 10.0.2.11# 12. 在对端也加 20mssudo ip netns exec r2 tc qdisc add dev r2-r1 root netem delay 20mssudo ip netns exec h1a ping -c 10 -q 10.0.2.11# 13. 对照：同机架通信不经过这条链路sudo ip netns exec h1a ping -c 5 -q 10.0.1.12# 14. 查看与清除sudo ip netns exec r1 tc qdisc show dev r1-r2sudo ip netns exec r1 tc qdisc del dev r1-r2 rootsudo ip netns exec r2 tc qdisc del dev r2-r1 root

              报告里给出预测值、实测值、以及差距的解释。重点解释这两件事：

              1. netem 挂在 root 上，作用的是出方向（egress）。这对"单向加延迟，RTT 增加多少"意味着什么？
              2. 实测值与预测值的偏差有多大？偏差来自哪里（ping 的时间戳精度、调度延迟、单机 CPU 争用）？
              NOTE说明

              本任务的具体数值未在课程仓库的验证环境中实机跑过（该环境的内核缺少 sch_netem）。命令本身是 tc 的标准用法，但如果你的实测结果与预期有系统性偏差，请在报告中如实记录，并告知助教。

              任务 6选做挑战

              把互联链路改成 /31

              路由器互联链路只需要两个地址，用 /30 要浪费掉网络地址和广播地址各一个。RFC 3021 允许在点对点链路上使用 /31，两个地址全部可用。

              把 ns_topo.sh 里的 10.0.12.1/30 与 10.0.12.2/30 改成 /31，重新搭建并验证连通性。然后回答：

              • 一个 40 机架、每机架 2 条上行的数据中心，用 /31 相比 /30 能省下多少个 IP 地址？

              第六节思考

              思考题

              1. 网桥为什么不需要配 IP 实验床里 br1 配了 10.0.1.1/24，但那是因为它兼任网关。如果 r1 只做交换、不做网关（网关在别处），br1 还需要 IP 吗？Docker 的 docker0 为什么有 IP？

              2. 路由能不能少配几条 三机架拓扑里，r1 需要两条路由分别指向 10.0.2.0/24 和 10.0.3.0/24，而它们的下一跳是同一个。有没有办法用一条路由覆盖两个网段？这样做的前提是什么？如果机架 3 的网段是 10.0.7.0/24 还能合并吗？ 提示：第 02 讲 3.3 节，以及 CIDR 的地址聚合。

              3. 脚本的幂等与真实运维 本实验的脚本靠"先拆后建"实现幂等。真实的数据中心不可能为了改一条路由就把整个网络拆掉重建。那么真实的网络配置工具（Ansible、NETCONF、各家的 SDN 控制器）是怎么做到幂等的？它们付出了什么代价？

              4. 故障的可观测性 任务 5 里有两对故障从源主机看现象完全一样。如果你是这个网络的运维，要在故障发生时自动区分它们，你会在哪些设备上采集什么指标？ 提示：想想哪些计数器会变——ip -s link、nstat、ip -s neigh。

              5. 延迟加在哪里 任务 4 把 netem 加在了路由器的接口上。如果改成加在主机 h1a 的接口上，h1a → h2a 和 h1a → h1b 分别会受什么影响？哪一种更像真实世界里"这条链路很慢"？
